# 列车移动接口与进站方向

2026-11-28 静态核对。范围为 Create 的移动物品、流体接口。未现场复现。包索引与实际 Forge 1.20.1 / Create 0.5.1.j JAR 的 SHA-1 一致，为 `fab2ae7fcf685b3875ca20022bfecf0d4fdafbf7`。以下按发行 JAR 的 javap 结果与 Create 源码对读。TrainResync 源码中未发现直接改写此接口搜寻逻辑的 Mixin。

- 进站定位。Navigation 反向导航时以末节车厢的 trailing point 作前端，正向以前车的 leading point 作前端。Carriage.travel 也按行进方向决定先处理哪只车轮。比较两次停车要对照的是同一车载接口的世界坐标与朝向；车站相同不能证明两次几何关系相同。
- 对接几何。PortableStorageInterfaceMovement.getActiveAreaOffset 把探测点沿接口自身朝向推出 1.85 格并转换到世界坐标。findStationaryInterface 只看探测点所在格及沿朝向再前一格；只接受同类、正对且未被红石供电的接口。斜向旋转离最近坐标轴的单位向量超过 0.5 时不搜寻。
- 触发时机。AbstractContraptionEntity.shouldActorTrigger 在服务端用列车速度绝对值缩放运动向量。常规 visitNewPosition 在探测点跨格或首次激活时调用，列车接口判定运动长度大于 0.25 格/tick 就直接返回。服务端 tick 没有 WorkingPos 时也直接返回，客户端低速时每 tick 仍然搜索。因此有可能跨进最后一格时太快、减速后停在同格，出现车上一侧伸出而地面未接通。代码能证明这条失效路径；没有位置和速度轨迹，不能断言这就是具体车站的原因。正负速度均有此限制。
- 复核手段。失败时保持列车静止，给站台接口一次红石脉冲。断电会走 neighbourChanged → notifyContraptions → refreshPSIs → visitNewPosition。若随后开始传输，说明停稳位置能建立连接，进站漏检值得优先验证。若本来两端已接合而相邻漏斗不出货，另查相邻方块的物品能力刷新。
- 上游记录。[#6731](https://github.com/Creators-of-Create/Create/issues/6731) 报告 0.5.1f 高速进站后车侧伸出、地面侧不接，红石复位有帮助，未证明与倒车绑定。[#9624](https://github.com/Creators-of-Create/Create/pull/9624) 已合入 mc1.21.1/dev，通过通知邻接方块修复漏斗能力刷新。[0.5.1j 变更记录](https://github.com/Creators-of-Create/Create/wiki/0.5.1j) 的修正针对组装时接口偶尔未连接。此次未找到针对 0.5.1.j 倒车到站漏检的已验证补丁。


## 补查加载器与倒车入库（已澄清为地面加载）

玩家报告按时刻表停车时煤水车补给失败，摘下时刻表并手动再次对齐后恢复。另有观察称组装时的 1 号车厢能对接，4 号车厢在倒车入库时即使有加载器也可能失败。AshBill 已澄清现场靠地面加载器覆盖，没有车载加载器。加载器的方块类型、是否附着车站、实际范围及现场有无玩家待核对。优先查保活覆盖，再对照前文的进站漏检。重新对齐同时改变了位置和检测时机，不能单独证明时刻表会禁用接口。

核对主服 2026-10-10 快照内 Create: Power Loader 1.5.0（SHA-1 与包索引一致）和 Forge 47.4.6 的字节码。快照和仓库主服模板均允许黄铜加载器在列车及车站工作，安山在这两种模式禁用，地面动力模式另算。黄铜车载范围值 2，对每个选中转向架采样点覆盖 3×3 区块。车站附着模式通过 getPresentTrain 判定已到站，以附着加载器的位置为中心。没有读实时服。

- TrainChunkLoader.tick 遍历整列车；CarriageChunkLoader 检查该车厢自身加载器，正常同维度线路用该车厢两端转向架的轨道采样点。Create 在本车厢 positionAnchor 所在区块允许实体 tick 时才创建缺失的车厢实体。同维度时锚点在该车厢组装方向的前转向架，倒车不会把锚点换到另一端。车载接口、锚点和站台补给设备要分别核对。
- 独立发现，与此次地面加载现场无关：车载多加载器存在以下冲突。每节车厢独立保存 forcedChunks，按差集增删；提交给 Forge 的所有者都是 train.id。Forge 47.4.6 的 TicketTracker 对同一所有者和 ticking 类型只存区块集合。同一列车两节各自启用加载器的车厢曾共同覆盖区块 X，一节退出而另一节持续覆盖时，退出方可撤掉该车在 X 的唯一票，留下方因自己的记录仍含 X 而不会补票。若没有其他有效覆盖，接口或该车厢实体可能停更。只在同列多节启用车载加载器且覆盖重叠时适用；本次不满足。该机制也不保证某个固定车号永远成功。
- 复现后先保留状态。从后台核对列车名、维度、地面接口和加载器坐标、加载模式与档位、4 号车厢组装方向前转向架锚点。对比加载器自报范围、Forge 的实际 ticking 票、车厢实体和煤的实际转移。玩家靠近、移车或红石刷新均放在取证之后。
- [Power Loader 1.5.0 源码](https://github.com/hlysine/create_power_loader/tree/1.5.0-mc1.20.1/src/main/java/com/hlysine/create_power_loader/content)；[Create #6566](https://github.com/Creators-of-Create/Create/issues/6566) 是无人时不补液、玩家到场才恢复的相似报告，模组清单同时列出 Create Chunkloading 和 Power Loader，未说明使用哪一种；[#3291](https://github.com/Creators-of-Create/Create/issues/3291) 的作者反馈不同加载器表现有别。未发现同时确认 Power Loader 1.5.0、组装尾车、倒车进站这三项的现成补丁。[上游变更记录](https://github.com/hlysine/create_power_loader/blob/main/CHANGELOG.md) 明确 1.20.1 的 2.x 起已停止支持 Create 0.5.1。

地面模式复核：Power Loader 1.5.0 的独立动力模式以加载器所在区块为中心，用方块坐标作 Forge 票的所有者，申请实体更新票；主服快照与仓库配置允许两种材质使用此模式，安山固定 1×1，黄铜可选 1×1、3×3、5×5。车站附着模式另按列车是否到站启用。站台接口在范围内不能证明煤水车的实体锚点也在范围内。若故障时两处均在实际实体更新范围，且车厢实体存在，转查停稳后服务端 WorkingPos 是否为空及供料设备状态。CarriageContraptionEntity 每节均执行 tickActors，之后才同步 SCHEDULED 标志。尚未复现或读取现场。


### 无人值守与回来恢复

Ruby 补充：只在站区无人值守时触发，玩家回来接口会恢复。这是玩家观察；回到现场后是否已实际转移燃料、是否曾移动列车或干预设备，尚无后台采样。复现优先让玩家在列车进站前离开车站模拟距离，保留时刻表、长停条件和原地面加载器。用相同列车及停位对照有人与无人两趟；另可比较到站已对接后才离开。取证应先于玩家返回，记录4号车厢实体、其锚点区块的实体更新状态、站台供料库存和实际煤量。玩家只靠近即恢复的观察降低固定错位和单纯速度漏检的优先级。主服历史快照和仓库模板的 ServerCore activation-range.enabled 均为 false，不能据此归因于按玩家距离跳过实体 tick。TrainDebugReport 的 at 只读 getChunkNow；loaded=true 不能证明实体更新。上游 Create #6566 也记录无人到站后停供、玩家到场恢复，未确定相同根因。

### 2026-11-28 再审：地面加载、无人进站、玩家回来恢复

- Create 0.5.1.j 在同维度按每节车厢组装时的前转向架定位实体锚点。Forge 47.4.6 的 ServerLevel.isPositionEntityTicking 同时检查实体管理器和距离管理器。只覆盖站台接口而漏掉煤水车锚点，就可能出现时刻表已到站、4 号车厢却没有实体执行接口更新。没有查到移动接口按车号或倒车方向禁用的分支。
- 车载接口在服务端已有 WorkingPos、朝向及目标有效时，会给地面接口续 keepAlive=2。地面端若继续更新而收不到续期，从 2 减到 0 时就会主动断开。玩家靠近没有专门的服务端重连回调。锚点恢复更新后可重新创建车厢实体；地面接口若重新初始化且无红石供电，也会通知附近移动结构重查接口。客户端自己会在低速时搜索，仅看伸缩动画不足以证明煤已转移。
- 主服历史快照和当前仓库更新源均含 Limited Chunkloading 4.1，配置为 10 分钟、无额外豁免、关闭 debugLog。按发行 JAR 的 EventHandler.onChunkLoad/onPlayerLeave/checkLoadedAndClear 核对：加载区块时记录本维度最近玩家（搜索距离参数为 -1）；找不到玩家则直接排队，已关联的玩家登出也会排队。到期后若关联玩家仍在线会跳过。仅离开站台、仍在线的已关联玩家不会因此启动登出计时。
- 确认两模组可能干涉：Power Loader 1.5.0 的地面加载器使用 Forge 的 forge:block_ticking。Limited Chunkloading 的内置豁免只加原版的五类票，主服配置未额外豁免此票；满足上述清理条件时它直接调用 DistanceManager.removeTicket，移除实际区块票。Power Loader 的 needsUpdate 检查方块位置、启用状态、范围和卸载延时，更新时基于自身 forcedChunks 求差集，稳定运行时不主动校验实际票。由此可能出现加载器记录仍含区块、实际的票已经丢失。现场加载器型号、票是否被删及具体时间均未取样，不能将这条兼容路径定为本次根因。
- 若拿到车名和坐标，在玩家返回前从后台按维度查地面加载器、地面接口、煤水车实体锚点和供料设备。Limited Chunkloading 4.1 提供 /limitedchunks listActiveTickets <x> <y> <z>，读取指定区块的直接票；使用 getBlockPos，不为目标添加加载票，会先处理已有的距离管理更新。空票不等于实体停更（相邻票可覆盖），需同时对照实际实体更新状态、4 号车厢实体和煤库存。保持列车静止，玩家回来后再查同一组。若实际票、实体、供料均正常，则转查车载 WorkingPos、地面连接和漏斗。复现区分“关联玩家保持在线、只远离”与“登出超过 10 分钟”。
- [Limited Chunkloading 作者说明](https://www.curseforge.com/minecraft/mc-mods/limited-chunkloading)；[Create #6566](https://github.com/Creators-of-Create/Create/issues/6566) 记录无人进站后直到玩家回来才开始输送岩浆，报告用 0.5.1f 并跨维度，仍开放，未确证同因。
