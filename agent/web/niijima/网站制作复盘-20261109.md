# 活动与反馈网页制作复盘

整理：2026-11-09。依据本次对话中的用户反馈、[素材与实现记录](README-event-art.md)以及当前页面实现。范围是这次活动页与长期反馈页制作，不是整站重构，也不把本次审美选择自动升级为所有项目的永久规则。

## 先看结论

这次有效的组合是：**用真实页面截图生成风格候选，以用户挑选的具体参考制作装饰素材；布局和交互保持真实网页；背景固定于视口，内容在其上滚动；用实际尺寸截图和交互来验收。**

最明显的失误是：只改 CSS 参数、只核对像素或计算样式，就把结果当作完成。用户要的是自然、好看、好用的页面；实现指标只能帮助验证，不能代替这个目标。

最终用户对固定背景的直接反馈是：“这个固定背景的效果意外的好，整个网页用起来都多了层专业感”。这项肯定针对实际浏览体验，不只是静态设计稿。

## 1. 美术方向：选中的参考比抽象风格词更重要

| 用户反馈／选择 | 本次有效做法 | 没有效果或走偏的做法 |
|---|---|---|
| 希望“日式网站风格、欢快感、活动感、装饰”，选择粉色版为基础 | 以现有页面截图和指定角色插画生成五份候选，再融合用户指定的局部 | 只凭这些关键词自由发挥，不能保证还原选中的样式 |
| 喜欢第一版 banner、背景波点，以及第4版邮票、胶带等装饰 | 把对应参考图／局部作为生成输入，统一色调、质感与比例 | 用简单 CSS 形状替代后，装饰的弯曲、纸感和层次明显不足 |
| 明确要求“素材都照着参考版为输入来 gen” | 背景、空邮票、弯曲丝带、胶带采用参考驱动的生成素材 | 生成一个同样叫“丝带”但厚重、立体、造型不同的素材，不能算还原 |
| 邮票比例更像第4版，丝带靠左上、略向左倾 | 分别锁定邮票比例、丝带位置与曲率，再调整文字 | 同时改变多个局部，容易把用户已经喜欢的特征改丢 |
| 邮票上的字需要更大 | 以参考中的文字／邮票面积比例衡量字号 | 只确保文字能放进去，结果信息层级偏弱 |

用户最初建议“能用 CSS 的地方最好还是 CSS”，但看到落地效果后，明确要求背景和装饰多用生成素材。应以这次后续反馈为准，不能继续用最初的原则解释明显不相似的结果。也不应反过来把整个网页做成一张图：真实表单、文字、布局和交互仍由网页实现；当前橙色 banner 也可继续使用 CSS。

## 2. 立绘：视觉质量与像素约束是两件事

| 过程 | 用户反馈／实际问题 | 经验 |
|---|---|---|
| 原图算法抠图 | 后来在叠加对比中发现边缘和背景残留很差 | RGB 没变只说明未重画颜色，不证明 alpha 抠得好。应分别检查轮廓、蕾丝、半透明部分和大块背景残留 |
| 第一版生成补全 | 用户喜欢自然的搭扣鞋；后来又指出残留一团黄色背景 | 一张图可以同时有值得保留的鞋子和必须修复的抠图问题，不能全盘推翻或全盘接受 |
| 将原画布像素硬贴回生成候选 | 原图截断的靴面与新鞋拼接出现接缝 | 锁定像素并不保证接缝自然。生成存在位置、线条、颜色和服装结构漂移，不能声称对齐就能完美拼接 |
| 再生成鞋子 | 用户认为不如第一版自然，并指出舞台服两边鞋不同很正常 | 不要为了对称或自认为的服装正确性，改掉用户已认可的造型；当时“不再生成”的要求应立即生效 |
| 从最初未抠图的原图重新生成 | 用户后来明确授权重做，取消裙摆奇怪缺口，保留第一版鞋子感觉 | 授权变化后才重新生成；原图作主要输入，旧候选只提供被认可的局部参考，避免继承旧抠图污染 |
| 第四版交付 | 用户明确选择第四版上网页 | 采用连续裙摆、粉色搭扣鞋与真实 alpha 的成品；它是生成重建，不是原像素锁定的扩图 |

本次 imagegen 实际返回过真实 RGBA 透明图片，因此“生成一定给不出透明背景”不成立。绿幕只是当时允许的备用方法，不能把没有使用的方案写成实际流程。同时，本次工具接口没有显式的像素锁定蒙版，提示词中的“保留原图”也不是逐像素保证。

透明素材应在浅底、深底和实际页面上分别看。叠加器很有用，但原图底层可能从新图透明部分透出；判断新素材是否干净，还必须单独看原始透明图。给用户展示时标明：原图、算法抠图、纯生成候选、硬锁定合成、过渡合成，不能混称。

原图右侧和底部本来就被截断。未补全前，直接把它挪离页面右缘会暴露截断；补全后再处理与表单的轻微交错。角色不能遮挡输入、按钮或截掉脚部，装饰层不接收鼠标事件。用户希望角色略大、有交错感，并不等于允许角色无约束地超出屏幕。

## 3. 丝带文字：沿弯曲排字，同时保留真实文本

用户指出原参考中的文字沿丝带弯曲，落地版却太平；之后明确要求只上下调整“试、期、间”，不要改变字距和角度。

最终方法是先确定沿路径的字符原点及旋转角，再冻结这些值，沿**每个字自己的上下轴**作小幅位移。同一个 SVG `text` 下使用 `tspan`，保留连续文本与整体选择，避免把字分别烧进图片或变成无法连续复制的独立块。已验证可复制为 `v1.6 测试期间`；本次三个字的下移值是 3／6／9 个 SVG 单位，不是其他页面通用参数。

一次局部调整只改用户指出的变量。用户已经说“间距和角度都不用动”时，重算整条路径、重新分配字距或倾角，会破坏其正在逐步确认的基线。

## 4. 背景：真正的问题是参照谁的尺寸

| 尝试 | 结果与用户反馈 | 结论 |
|---|---|---|
| 背景 `100% 100%` 随页面双轴铺展 | 多比例对比中发现拉伸，用户明确否定 | 保持图片比例；需要更多画面时可扩图，不靠变形填满 |
| 对整个长页面使用 `cover` | 文档越高，背景越被放大裁切；iframe 缩短又触发缩放 | `cover` 本身不是错，错误在于把变化的内容高度当作背景参照 |
| 透明父容器保留 iframe 最大高度 | 切换 Bug／建议时页面高度更稳定 | 对稳定布局有效，但没有解决背景绑定整张长页面的问题 |
| 对整个长页面使用 `contain` | 背景成了中间一条横带，上下明显断层，手机几乎看不到装饰；用户指出“broke” | 机械执行参数仍可能违背目的。不能把这种明显坏效果解释为“预期留白”然后交付 |
| 独立背景固定于视口，居中 `cover` | 屏幕始终铺满，内容滚动时背景不动，iframe 高度不再影响背景；用户明确称赞专业感 | 本次最终采用，替代上面两种基于文档尺寸的方案 |

当前实现位于 `dist/assets/event-pink.css`：`body.pink-event` 建立隔离层，`::before` 使用 `position:fixed; inset:0; z-index:-1; pointer-events:none`，背景 `center / cover no-repeat`。先前将固定层放在内容场景内时盖住了导航栏，移至 body 的后方才正确；所以还必须检查层级，不能只检查铺满。

图片不能同时在任意比例下做到“完整显示、不留空、不裁切、不拉伸”。应先说明取舍，再按用户目标选择。本次用户最终接受等比铺满的边缘裁切，重点是视口适配与滚动体验。不要把这次结论扩成所有网站都必须固定背景。

## 5. 页面结构与信息：少做用户没有要求的东西

- **长期反馈本体与短期活动外壳分开。** 活动页内嵌同一反馈页，反馈页也能独立使用。通过 URL 参数隐藏嵌入场景中重复的导航，避免复制维护两套表单。
- **让 iframe 配合页面。** 足够高度、正确的高度消息与必要的父容器占位，有助于避免双重滚动和页签切换跳动；但背景稳定应由独立背景层负责。
- **导航精简。** 用户澄清是“图标”返回首页，随后移除重复的右上返回入口；navbar 使用实色条。底栏、重复 logo 和英文 `NIIJIMA RAILWAYS` 行被要求删去。本轮没有为了填空而添加新内容。
- **标题位置不要猜。** 用户要求波浪线包围的完整活动名在页内顶部单独一行，不是浏览器标签标题，也不是分散在正文里。最终 banner 为 `~~祝整合包v1.6测试！bug报告返金倍率up期间开催中！~~`，波浪线作为真实字符保留。
- **品牌使用真实资产。** 橙色 N 图标与「新島鉃道」矢量字标复用已有素材，不采用生成稿中可能变形的字形。浏览器标签最终为「新島鉃道」（鉃，U+9243）；favicon 使用 N logo 已记录为部署事项，不能说已经配置。
- **表单按用户最终选择收敛。** 两种反馈都必填游戏内 ID，不假定日志总能可靠提取；Bug 必须有错误报告附件，功能建议隐藏整个附件框，提交时也不携带先前选择的附件。
- **标签与文件限制分开。** 显示文案叫“错误报告”，但不限制扩展名，拍屏等也能上传。最终规则是附件合计 10 MiB，含文本 JSON 的外层 ZIP 最多 11 MiB；用户传入的 ZIP 也可以作为附件再封装。不要把早期的 20／100 MiB 讨论当现行规则。
- **没有接口不等于表单不能操作。** 上传地址待配置时禁用提交，不应让页签或输入失效。用户已否定“复制反馈再发送”流程，不能为演示方便恢复它或模拟提交成功。

上述是本次已确认的选择；新文案、新交互和新的产品窗口仍须依项目协作规则讨论，不应由 agent 自行补出一整套流程。

## 6. 验收：看实际效果，而不是证明自己写了某个值

这次最需要纠正的是：用户要求检查六图，agent 却在看到 contain 的明显断层后，仍以“计算样式正确、无横向溢出”为由宣称通过。这样的验收没有回答用户的问题。

下次同类改动采用以下范围即可，不扩成重复的大检查：

1. **参考稿与落地截图并排。** 对比比例、曲率、字号、留白、交错关系；不要只凭记忆说“差不多”。
2. **逐张看六档实际首屏。** 本次使用 2560×1080、1920×1080、1440×900、1024×768、768×1024、390×844；检查断层、导航遮挡、文字和角色裁切、横向溢出以及表单可达性。
3. **首屏与全页明确区分。** 全页图可能比视口长得多，不能把其整张比例标成屏幕比例；总览卡片空白也不能让用户误以为是网页空白。截图尺寸异常时核对实际图像，不能只相信设置的 viewport。
4. **只验证相关动态状态。** 背景修改检查滚动和页签切换；素材修改检查透明边缘与遮挡；文字修改不重复上传测试。代码改了或发现异常时才重拍受影响内容。
5. **交互失败要查浏览器实际响应。** 本次 iframe 不能操作不是预期：预览服务把 `.mjs` 返回为 `text/plain`，导致模块未执行。改用正确返回 JavaScript MIME 的 `.js` 后恢复；语法通过和 HTTP 200 都不足以证明脚本已运行。
6. **明确验证边界。** 本机预览、静态检查、浏览器交互通过、真实上传联调、正式部署是不同状态；没有配置收件服务，就不能宣称上传成功或上线完成。

浏览器操作仍以明确授权为前提。此前只允许静态检查时应如实说明局限，不能把静态验证写成实际使用通过；得到本次浏览器许可后，才进行相应预览和截图。

## 7. 下次可直接复用的制作顺序

先锁定用户目标和现有功能；用当前截图生成少量候选，让用户指出喜欢的局部；从选中的参考生成单个装饰，复用真实品牌与文本；实现布局后尽早作一次参考对比，再做细小位置调整。资产有争议时用独立透明预览和叠加器解释区别，不反复重生成已经满意的部分。

交付前检查相关尺寸和动态状态，发现明显视觉错误就修正，不能用“实现符合参数”代替结果。只把最终需要的素材放进部署目录，候选、提示词、对比页和截图留在独立工作区。记录当前采用版、被否定版以及否定原因，避免下个 agent 重走同一条路。

本次有价值的验证是找出断层、层级、MIME 和透明边缘问题；没有收益的工作是为已经通过且未变化的功能重复跑检查，或为保持像素指标牺牲用户认可的视觉效果。阶段计时应帮助识别这些返工，而不是成为额外的工程负担。
