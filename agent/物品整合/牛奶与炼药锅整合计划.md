## 用户指定的整合目标（2026-10-16，优先于下文早期备选方案）

本节最初为用户要求记录的目标，随后用户授权先在临时模组实施并放入实例；实施状态见末节，不代表已通过游戏测试。

1. **奶瓶统一**：OEI 将 `neapolitan:milk_bottle` 统一到原先已有的农夫乐事 `farmersdelight:milk_bottle`，不以那不勒斯奶瓶为目标。
2. **统一建锅入口**：奶桶右键普通炼药锅、奶瓶右键普通炼药锅，以及向普通炼药锅输入牛奶流体，均转为 `amendments:liquid_cauldron` 并存入对应奶量。不能被那不勒斯或自然之灵的原有交互抢先替换成其奶锅。此处按牛奶专项记录；是否扩展其他流体并覆盖原版水／岩浆行为，用户尚未指定。
3. **自然之灵加工出口**：Amendments 锅满奶时，用蘑菇交互进入自然之灵对应的制酪锅／熟成流程。具体沿用 `cheese_maker` 标签还是扩大为其他蘑菇、转换时的方块与熟成状态、物品消耗，实施前需按原机制核对；不能擅自解释为任意蘑菇都能立即产出成品奶酪。
4. **那不勒斯加工出口待定**：用户尚不清楚其奶锅有哪些后续操作，先列出已审计功能供后续讨论，不自行决定删除或全部移植。此前查到冰淇淋将奶锅转为对应奶昔锅，以及接触清效果、滴水石加奶；这些是原功能事实，不是本次已确认的整合需求。
5. **统一取奶出口**：空瓶、空桶右键或流体系统抽出，均从 Amendments 锅取出对应的牛奶；奶瓶输出使用农夫乐事奶瓶。按拟定容积单瓶 250 mB、整桶 1000 mB，数量不足时不得凭空补足，满量制酪条件与奶量账本保持一致。
6. **空锅与掉落（同日用户修订）**：用户确认既然已补普通锅入口，抽空后即可沿用原逻辑恢复普通炼药锅，再从瓶、桶或机械动力管道重新装奶；取代先前“保留空 Amendments 锅”的要求。挖掉时掉落普通炼药锅，现有 Amendments 掉落表已满足，无需改写。

实现时重点验证：普通锅首次接收流体的入口、抽空恢复普通锅后管道能重新识别并继续灌奶、奶量守恒、旧交互优先级，以及满奶锅进入自然之灵熟成流程。此前提出的两旧锅并存方案仅保留为调查历史，不再作为首选交互设计。

### 那不勒斯奶昔锅原机制补充（2026-10-16）

按安装版 5.1.0 的 `NeapolitanCauldronInteractions` 字节码复核：用对应口味冰淇淋右键其牛奶锅，生存模式消耗一个冰淇淋并返还碗，立即把当前整锅换成对应奶昔锅，通过 `transferAllBlockStates` 保留 LEVEL；不要求满锅、不需要加热或等待。原锅 1／2／3 层分别可用玻璃瓶取出 1／2／3 瓶奶昔，每次取一瓶降低一层，最后恢复空的普通锅。满奶桶灌入原奶锅设为三层，因此一个满奶锅加一个冰淇淋可产三瓶奶昔。六种入口为香草、巧克力、草莓、香蕉、薄荷、红豆。此为原模组代码行为；包内建锅入口可能被其他模组争抢，尚未实测。

四瓶制 Amendments 锅不能直接套用原三层状态来推断产量；整锅转四瓶、限定三瓶批次或其他数量方案仍待用户决定。

## 结论

建议以农夫乐事奶瓶作为统一物品，按 **1 瓶 250 mB、1 桶 1000 mB、4 瓶回桶** 统一容积。不能先单独合瓶再修行为：那不勒斯原本是三瓶回桶，且牛奶锅按三层运行；与机械动力的 250 mB 奶瓶灌装组合已经存在数量不守恒的静态配方路径。

具名牛奶炼药锅有自然之灵与那不勒斯两种，另已确认 **Amendments 通用液体锅 + Moonlight 牛奶映射 + Supplementaries 水龙头** 这一套流体兼容。它使用 `amendments:liquid_cauldron` 保存奶，没有另一个叫 milk_cauldron 的物品。用户提醒应查流体兼容后，已追踪安装 JAR 的实现；不能再将本包储奶锅概括为只有两个方块。本轮仍未游戏验证最终交互优先级。

方案优先级修订：先评估复用 Amendments 现成四份容量的通用液体锅，再桥接那不勒斯与自然之灵的加工功能；不以“先新建一个奶锅”为默认实现方向。详细依据及接口风险见末节。

## 两种牛奶炼药锅

| 方块 | 现有实现 | 必须保留或处理的功能 |
| --- | --- | --- |
| `neapolitan:milk_cauldron` | 继承三层炼药锅；桶倒入设为第 3 层；瓶每次增减一层；满锅可用空桶取出奶桶 | 分瓶、装桶、踏入液面清除随机效果并消耗一层、滴水石填充 |
| 那不勒斯六种奶昔锅 | 牛奶锅与对应冰淇淋交互转成奶昔锅；代码转移原方块状态 | 香草、巧克力、草莓、香蕉、薄荷、红豆奶昔；保留口味、效果和容器返回 |
| `natures_spirit:milk_cauldron` | 不继承三层锅；以 `age_into_cheese` 布尔状态控制熟成 | 棕色蘑菇（`natures_spirit:cheese_maker` 标签）触发熟成，随机刻转为奶酪锅，桶取奶／奶酪 |

那不勒斯本机配置：Milk Cauldron=true、Milk from Dripstone=true、Milkshake Cauldrons=true、Milking with Glass Bottles=false。仓库未找到显式覆盖这些选项；本机值不等于所有服务器存档实际配置。

自然之灵不是简单注册一个同名配方：`NSEvents` 监听 RightClickBlock，对炼药锅标签里的方块使用奶桶时（排除它自己的奶锅），直接替换成自然之灵奶锅并处理桶。那不勒斯则通过 Blueprint 注册奶桶和奶瓶交互。两套入口有竞争，需要控制事件及方块交互次序；不能只在配方层解决，也不能仅凭静态代码宣称当前每次操作的最终结果。

那不勒斯锅的瓶输入和输出按具体 Item 注册，OEI 的配方替换不等于重写这些 Java 交互。仅合瓶后，必须验证统一奶瓶还能倒回锅，取出的是否仍是旧奶瓶，避免“看着统一、行为未统一”。

## 推荐方向与待选方案

### 第一层：统一奶瓶及基础容积

1. OEI 将那不勒斯奶瓶统一到农夫乐事；保留原版奶桶和现有奶流体，不新造另一种奶。
2. 两套手工分装／回桶统一为四瓶制，或在统一后仅留一套等价配方；返还空桶与空瓶。机械动力保持每瓶 250 mB，去掉重复项并处理排液资源错误。
3. 检查两套细分奶瓶标签，保持特色食品／奶昔／奶茶入口。装饰奶不纳入食物统一。
4. 普通食物使用 `forge:milk` 时一桶与一瓶可互换属于另一层平衡问题：逐项列出高影响配方再讨论，不在此次悄悄把所有食物用奶量重算。

### 第二层：锅的功能与自动化

**建议目标是统一用户操作和奶量，而不是立即删除原方块 ID。** 两种旧锅都要有兼容路径，避免已有世界中的锅失效。

| 方案 | 优点 | 代价／限制 |
| --- | --- | --- |
| A：保留两种锅，补明确的转换与交互 | 改动较少，奶酪和奶昔各留原入口 | 仍有两个锅；那不勒斯三层与 250 mB 的冲突仍必须完整解决，不能只加互换配方 |
| B：统一奶锅操作，内部保存 0–1000 mB，四份奶瓶 | 与桶／瓶／机械动力一致，能保留清效果、奶昔、奶酪等功能 | 需要 Java 方块／行为兼容层、明确旧状态迁移；是否新增自有方块或扩展现有方块待设计 |

倾向 B，但尚未请求实施：奶瓶每次 ±250 mB，整桶 ±1000 mB，满量且未转化的奶锅才允许整桶取出；加奶不得静默溢出。三层旧锅不能直接解释成每层 250 mB 后仍允许第三层取一整桶。也不能把全局原版炼药锅 LEVEL 改成四层，影响水、雪与其他模组。

功能细节须一起决定：奶酪只从满量奶锅开始熟成；奶昔转换按现有食谱产量明确消耗奶量与保留余量，不能因四份奶变成一锅就默认把原三瓶奶昔增产成四瓶；清效果消耗奶量、滴水石每次增加量也需定值。自然之灵的奶酪锅作为加工状态可保留，无须强行把它也当普通奶容器。

锦致装饰水龙头、Amendments 增强炼药锅、机械动力泵与管道属于后续验收矩阵。包配置启用 enhanced_cauldron；本轮没有确认所有现存锅都提供可供泵读取的流体能力，不能承诺“加流体标签就自动通”。若统一锅要直接支持泵送，需要明确提供流体能力并使手动与自动操作共用同一数量账本。

建议实现分工：OEI 管物品统一；KJS／数据包管配方与标签；必要的 Java 兼容代码管状态、事件、容器交互及流体能力。是否放入 TrainResync 或独立兼容模组由用户后续决定，本轮不创建工程。

Amendments 官方介绍也明确称炼药锅可存放各种液体：[项目说明](https://modrinth.com/mod/amendments)。这是功能背景；上述具体容量和类调用以本包安装 JAR 为依据。

### 不能跳过的接口风险

安装版 Amendments 2.2.3 的 `SelfCauldronMixin` 静态检查发现单位／契约不一致候选：`fill` 返回 `SoftFluidTank.addFluid` 的整数份数，没有像容量查询那样转成 mB；`drain(int, action)` 直接将调用方的数量传给按软流体份数工作的 `removeFluid`，没有先除以 250；`drain(FluidStack, action)` 只转交数量，没有在这一层核对请求流体类型。执行 fill 分支还会 shrink 调用方 FluidStack。Moonlight 的 add/remove 方法已核对，参数／返回确实按软流体份数处理。

因此“存在 Forge 流体能力”不等于“机械动力抽灌已正确”。这些是安装字节码中的具体问题线索，尚未做游戏复现或确定是否有其他层规避。下一步应以 250/500/1000 mB 及不足 250 mB 的请求检查 SIMULATE 与 EXECUTE 返回量、实际存量和流体类型；不要直接假定完整泵送安全并宣传已兼容。
