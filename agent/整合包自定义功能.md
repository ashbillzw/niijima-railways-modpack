## 方案讨论（2026-10-12：野生稻米改为局部掉落替换，未实施）

用户询问能否用 KJS 避免维护完整覆盖表。原则上可以；将整表原样转为 JS 重建不会降低维护负担，应只保留目标修改。当前索引 KubeJS 为 2001.6.5-build.16，未发现 LootJS 条目。本地对应 KubeJS JAR 的 LootEventJS.modify 支持编辑已有 LootBuilder.pools，但 LootBuilder.toJson 只输出 type/pools/functions/conditions，不保留 random_sequence 等其他顶层字段，因此不能声称该便利 API 完全无损保留新版原表。

更适合讨论的方案是 KubeJS + LootJS：限定 farmersdelight:blocks/wild_rice，使用 replaceLoot 将生成结果中的 farmersdelight:rice 换为 kaleidoscope_cookery:wild_rice，第三参数 true 保留数量。按当前原表，剪刀产物是 farmersdelight:wild_rice，不匹配替换；无产物时不会额外补发；相邻方块、工具、爆炸等判断由原表负责。来源为 [LootJS 官方 1.20.1 文档](https://github.com/AlmostReliable/lootjs/wiki/1.20.1#replaceloot)。此为方案，不是安装或实施决定，也没有游戏验证。

代价与迁移条件：需用户确认新增 LootJS；实施时旧同名覆盖表应与替代脚本同批移除，才能恢复读取上游资源。当前 OEI 也替换 farmersdelight:rice，需要核对修饰器执行顺序并实测，不能直接宣称与当前包等效。后续升级仍检查表/物品 ID 与玩法变化，只是不再手工维护整表。此前“更新原覆盖表”的待办继续有效，直到用户决定采用替代方案后再调整。

### 4. 野生稻米：字段实际漏掉什么

文件：`pack/overrides/kubejs/data/farmersdelight/loot_tables/blocks/wild_rice.json`。

外层 `predicate.block` 表示“检查目标位置的方块”，合法；内层 `block: "farmersdelight:wild_rice"` 才是错误，正确形式为 `blocks: ["farmersdelight:wild_rice"]`。现在解析器忽略这个内层字段，但仍检查 `half: upper/lower`。

所以它不是“野生稻米一定不掉落”，也不是“无条件掉落”：正常完整稻米满足两种写法，往往看不出差别。差别是相邻位置如果是**其他也有相同 half 属性的方块**，旧条件也可能通过。这是校验被放宽，不是已经证明可稳定刷物品。

基本回归：在生存模式分别从上下半部破坏完整野生稻米，分别用剪刀与空手测试。剪刀应保留农夫乐事野生稻米，非剪刀应得到森罗物语野生稻米；记录实际数量及有无额外掉落，不把创造成破坏当测试。

要直接区分字段效果，可在**临时测试数据包**放两个 predicate（本轮未创建或安装）：

```json
// data/audit/predicates/rice_old.json（实际JSON文件中不要写此注释）
{"condition":"minecraft:location_check","predicate":{"block":{"block":"farmersdelight:wild_rice","state":{"half":"upper"}}}}
```

```json
// data/audit/predicates/rice_fixed.json（实际JSON文件中不要写此注释）
{"condition":"minecraft:location_check","predicate":{"block":{"blocks":["farmersdelight:wild_rice"],"state":{"half":"upper"}}}}
```

测试数据包使用1.20.1的 pack_format=15，放测试世界 datapacks 中并 `/reload`。把 X Y Z 换成一朵向日葵**上半部**的坐标：

```mcfunction
/execute positioned X Y Z if predicate audit:rice_old run say old_MATCH
/execute positioned X Y Z if predicate audit:rice_fixed run say fixed_MATCH
```

按已核对的解析器，旧条件通过、修正条件不通过；换为真实野生稻米上半部，两者都应通过。这个定点测试不必制造会触发邻居更新、自动断裂的“稻米+向日葵”混合植株。尚未实测，不宣称测试通过。

### 5. 礼包：rolls 与 count 的区别

文件在 `data/yuushya/loot_tables/blocks/` 下，涉及 businessman、cook、electrician、gardener 四份；提示位于 `assets/yuushya/lang/zh_cn.json`。

- rolls 是抽奖次数，每次按 weight 选一个奖励条目；同一条目可以重复抽到。
- 条目自己的 set_count 决定这一抽给多少个物品。
- 电工礼包 rolls=1，但抽到 mounted_tv_online 时 count=3，因此可能给3台电视。
- 商人礼包 rolls=3，海报条目每抽 count=5；三抽都抽到海报就可能共15个物品。3次不等于3个。
- 目前修改只有抽取次数，未修改上游每项 count。最小文案方案是“抽取1次/3次”，不是擅自改变奖励数量。

生存模式连续放置、打破多个礼包，并记录每次得到的物品种类和数量。也可用下列命令快速重复抽取电工奖励（命令直接执行掉落表，不验证方块是否正确绑定该掉落表；至少实际打破一次作为补充）：

```mcfunction
/loot give @s loot yuushya:blocks/electrician_gift_box
```

每次先把上一轮物品移开便于计数。电工36个等权条目中仅某些条目多件，一次没抽到不能证明“每次只给1个”。最终核对工具提示与实际意义是否一致；当前提示尚未修改。

## 已确认问题与风险

### 1. OEI 使用了当前版本不读取的旧配置字段（优先处理）

包内与两服 `config/oei/common.json` 内容一致，都写有 `Data_Rewrite_Mode`、`Tag_Rewrite_Mode`、`recipe.Data_Dir_Rules`。

但匹配当前索引的 OEI 1.0.5.1 `Config.init()` 只注册三个布尔选项和 `common.Default_Rules`。后者的 Codec 使用 `data`、`tag` 映射；数据/标签处理通过 `Replacements.Rules`、`ReplacementCache.shouldReplaceInDataDir/shouldReplaceInTagType` 判断，没有配置时默认不启用该重写路径。现有 17 条规则也都没有单独的 rules 字段。

因此旧字段写了值，不代表配方 JSON、进度 JSON 或标签按旧意图重写。物品栈层替换仍能运行，不能反过来声称整个 OEI 失效。这种“物品看起来统一了，但底层配方/标签未按预期处理”的状态值得优先解决。

2026-10-10 快照 KJS 日志中，映射为空气的铋晶体、偶像礼包、车站和遮光框架玻璃等配方仍进入解析并出现 `ItemStack 'result' can't be empty!` 警告，与两种处理层不一致相吻合。调整 Default_Rules 会影响行为，应单独讨论目标后实施，不能混进纯文件整理。

### 2. `pantographsandwires:steel_wire` 不存在（明确无效规则）

`data/oei/replacements/iron_copper_wires.json` 第一条规则无效。本版 `ModItems` 没有注册这个 ID；快照 `logs/latest.log:447–448` 明确报来源不存在、该条没有有效来源。铜线规则正常加载。

不要凭名称自动改成 `power_wire` 或 `wire_coil`，这些不是已经证实等价的材料。应确认原意后移除过时映射或指定正确来源。

### 3. 画师礼包合成保留了未使用的 `X`

`data/yuushya/recipes/painter_gift_box.json` 的 pattern 只使用 `B` 和 `#`，key 仍包含 `X: yuushya:the_encyclopedia`。对照原 JAR，原配方 pattern 使用 X，整合包改了 pattern 后没有清理 key。

这是确定的定义残留。Minecraft 1.20.1 和 Forge 47.4.6 的 ShapedRecipe 校验会对未用键抛出 `Key defines symbols that aren't used in pattern`。但快照日志未检索到该配方同名错误，本轮没有实际跑完整模组组合，因此不能称已经在当前包复现礼包不可合成。最小修正方向是移除未使用的 X，不改现有材料布局。

另一文件 `recipes/block/painter_gift_box.json` 的 `{}` 不是本版 KubeJS 下必然报错：已经核对 `RecipeForgeHelper.checkConditions`，缺少 type 时返回 null 并跳过。它是在禁用原切石配方。可考虑将它改为显式 `event.remove({id:'yuushya:block/painter_gift_box'})` 以便阅读，但需和删除覆盖文件同时处理，否则原配方会回来。

### 4. 野生稻米掉落表含无效的内层字段

`data/farmersdelight/loot_tables/blocks/wild_rice.json` 两处 `location_check.predicate.block.block` 使用单数 `block`。本地 1.20.1 `BlockPredicate.fromJson` 读取的是 `blocks` 数组；这个内层单数字段被忽略，实际没有按 ID 限定相邻方块，只保留 state 等其他检查。

此问题已存在于快照农夫乐事 1.2.9 的原掉落表，不是整合包修改掉落物时新增。本机没有 1.3.4 JAR，不能确认新版上游是否已修复；整合包的整文件覆盖仍保留旧写法。不能把外层合法的 `predicate.block` 或 `block_state_property.block` 一并误改。

### 5. 礼包提示说的是“个数”，配置实际上是“抽取次数”

四个礼包只改了 rolls，保留原 entries 和各自 count。例如电工礼包抽一次 `mounted_tv_online` 可得 3 个；商人礼包抽到海报每次可得 5 个。因此“修改为1个/3个”不准确，应考虑写“抽取1次/3次”，不擅自统一 count 改奖励。

四份表 `survives_explosion` 下还有 `block: yuushya:food_gift_box`。这是上游复制残留，本版该条件解码根本不读 block，不会因此检查错礼包；属于可清理冗余而非必然掉落错误。

### 6. 语言文件整份覆盖过大

`assets/farmersdelight/lang/zh_cn.json` 共 289 条；与快照 1.2.9 对照，288 条相同，仅 `farmersdelight.jei.info.dough` 改了文案。升级到 1.3.4 后，这些旧翻译会继续覆盖相同键的新上游翻译。建议只保留要覆盖的这一条；由于当前版本更新，这也可能恢复新版文案，应作为明确资源整理项说明。

### 7. 新村民标签的发布依赖尚未衔接

当前 TrainResync 源码已有 `LeashableTagMixin`，mixin 列表也已注册，读取的正是此标签。包索引仍引用 1.6.0.e，服务端主服实际源文件仍是 d，当前源码为 g；这个新脚本不能单独证明发行包已支持村民牵引。交付时需要确认包含该实现的 JAR 并同步索引/两服。此次未改版本或下载。
