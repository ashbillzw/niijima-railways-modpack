# 2026-11-17 · Windows 上 Codex 桌面端请求超时

## 现象与排查

Codex 桌面端发送消息时连接超时，同机浏览器仍能使用 ChatGPT。对同一 HTTPS 检测地址做了三次 curl 对照：显式指定本地代理、经 Proxifier 透明转发、在透明转发下固定目标 IP。三次均返回 HTTP 200。这说明测试时这几条路径能承载 curl 的 HTTPS 请求；桌面端自身的请求仍需单独验证。

## 恢复经过

排查时发现 Windows 手动代理已关闭，但当前用户的 `ProxyServer` 仍保存旧地址。随后在 Codex 用户目录的 `.env` 中显式设置本地代理，并在备份 Windows 设置后清除旧地址。用户随后确认桌面端恢复。两项变更之间缺少单变量对照，无法确定哪一项对恢复起了决定作用。

## 临时配置与收尾

恢复后的只读检查发现，Codex 会话继承了 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 和 `NO_PROXY`，桌面端进程也有到指定本地代理端口的已建立连接。Proxifier 保留原有冗余链。Windows 手动代理关闭，旧地址和 PAC 地址均为空，WinHTTP 为直连。

同日移除仅含上述四项的 Codex `.env`，并确认用户级、系统级环境变量中均无这四项。保留注册表备份和 Proxifier 配置。删除文件后，已启动的会话仍继承原环境。记录时尚未在完全退出并重新启动的桌面端验证发消息。

### 已核对的本机状态

- Proxifier 活动配置为 `Default`，其个人域名规则直连，其他 TCP 走冗余链：UCSS 44554 → v2rayN 10808 → LMCloud 7892。取样时只有 44554 在监听，另外两个端口没有监听；配置上的备用节点当时不能提供备用服务。
- `ProxifierDrv` 与 `ucss` 两个驱动均在 Running，UCSS 的 Meta Tunnel 网卡也在 Up。UCSS 保存配置的全局与 DNS `ipv6` 均为 false；Ethernet IPv6 绑定仍启用，没有 IPv6 默认路由。
- 默认双栈测试的 DNS 结果仅有 A 地址。固定同一 IPv4 地址后仍按 socket family 区分成败，故不能只归因于 IPv6 DNS 返回或缺少公网 IPv6。
- Windows `ProxyEnable=0`，`ProxyServer` 和 PAC 地址均为空。旧 10808 注册表值已经清除，但默认双栈故障依然可复现；它无法解释当前全部症状。
- Codex `.env` 已不存在，但当前会话仍继承指向 UCSS 44554 的四个代理环境变量。当前会话的连接成功不能证明“重启后不带这些变量也已恢复”。
- UCSS 日志另有对原生 IPv6 目标的 `dns resolve failed: ip version error`。这是一类独立可见的 IPv6 出站失败，不能与本轮“IPv4 目标经双栈 socket 被拒”混为一谈。

Java 默认可用 IPv6 socket 承载 IPv4 连接，`preferIPv4Stack=true` 才限制为 IPv4-only socket；这与当前对照相符，见 [Java 17 网络属性](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/net/doc-files/net-properties.html)。此参数是本机绕过措施，不应自动推广给所有玩家或全球禁用 IPv6。

### 02:28–02:33 根因修复研究：新增 IPv6 回环异常证据

实测与版本：

- Proxifier EXE 4.14.0.1、驱动 1.0.120.2；UCSS 5.2.5。官方 changelog 当前最新列出 4.14，故“升级 Proxifier 就能修好”没有版本依据。4.03 的 IPv4-mapped 修复属于已包含的旧修复，不能当成本机待安装的修复。
