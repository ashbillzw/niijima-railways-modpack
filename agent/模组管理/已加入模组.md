## 结构与维护约定

用户已确认：本表同时登记客户端与服务器模组。仅服务器需装的模组可能只存在于远端，不在 index 中属于正常情况，不据此判为遗漏或要求补入。

将“模组身份、原表版本、当前索引、部署策略、前置、历史备注、审查问题”拆开记录。JSON 使用持久 `id` 关联前置，Excel 行号只保留用于追溯；名称按官方项目或当前本地 JAR 统一，原始名称不丢弃。

“服/客”是原表的部署选择，尚未重新确认；不能与 Modrinth 项目级 `required / optional / unsupported` 等同。表中“索引未收录”只描述当前整合包。库可能内置于其他 JAR，不能看见依赖名就要求独立安装。

前置栏的“原表”表示尚未完整验证；“候选”表示日期/相对行号恢复推测；“校正”只针对本次有证据的关系。完整的强制/可选、版本范围与侧别见 JSON 的 `matching_jar_evidence.dependencies`；证据为 null 不等于无依赖。

JSON 保存全部 126 行非空原始单元格值、日期类型、格式及删除线，且记录源文件 SHA-256。它是审查快照，后续修改 index 后应重新核对；不要直接用本表生成服务器包。

## MCEF 双实例加载逻辑排查（2026-10-12）

用户报告同机两个独立游戏目录启动时，第二个实例无法加载 MCEF；明确要求先分析逻辑，不读取日志。

- 当前 TrainResync 仓库 `TrainResync/src/main/java/com/ashbill/trainresync/mixin/mcef/MCEFDownloaderMixin.java` 第 23–25 行把运行库统一定位到 `%LOCALAPPDATA%/AshBill/mcef-libraries/<platform>`，不含游戏实例标识。第 39 行每次启动无条件 `FileUtils.copyDirectory(source, runtime)`，之后才设置库路径并跳过官方下载。相关提交为 `e47d517`（Extract bundled MCEF archive and overwrite local runtime）。
- 最直接的代码级解释：首实例已加载共享目录中的 DLL，第二个实例仍尝试覆盖同一批文件；Windows 对正在使用的目标文件可能拒绝覆盖。IOException 沿当前方法抛出，无法正常完成此次运行库准备。这解释了为何独立游戏目录仍相互影响；并非同一 DLL 天生只能由一个进程读取。

### 复制失败后的控制流（2026-10-12 补充）

已继续核对本机 MCEF 源码：TrainResync 的 copyDirectory 抛 IOException 后，后面的库路径设置及 callback.setReturnValue(true) 不会执行；外层 CefDownloadMixin 捕获该异常，打印 `Failed to download JCEF checksum.`、设置 failed=true 并 return，无法走到 done=true。CefInitMixin 仅在 done && !failed 时调度 MCEF.initialize；failed 分支只打印 `MCEF failed to initialize!`。因此当前不会在复制失败后自动尝试加载共享目录中的既有库；这条路径结束的是 MCEF 初始化准备，不等于主动退出整个 Minecraft。日志标题虽写 checksum，异常实际可能来自注入的本地复制。

可以设计失败后的加载回退，但应先确认目标库完整且匹配所需版本，再设置 mcef.libraries.path / jcef.path 并正常返回成功；不应吞掉任意复制异常后直接继续，因为目录可能半复制或混版。更合理的是复制前校验可复用库，避免先覆盖后回退。本次只分析控制流，未改代码或读取日志。
