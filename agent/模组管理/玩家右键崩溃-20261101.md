# 玻璃罐与电梯门右键崩溃 · 2026-11-01 玩家报告

2026-11-04 核查。新岛铁道 v1.5.1.m，Minecraft 1.20.1，两次均为客户端 Render thread。原始材料存于仓库外 D:/mydata/Agents/Minecraft相关/临时分析/玩家崩溃-20261101/。两份 ZIP 内的 crash TXT 均与单独提供的文件逐字节相符；以下同时核对了 latest.log 和本机对应版本 JAR 字节码。

- **附魔台，单人档。** latest.log 17:44:26.443；crash-2026-11-01_17.44.32-client.txt 第 18–23 行。Supplementaries 1.20-3.1.18 的 XPBottlingBehavior.tryPerformingAction 第 66 行在 JarItem 分支调用 Moonlight 1.20-2.16.15 的 SoftFluidTank.interactWithItem，调用字节码 173、174 明确给 Level、BlockPos 传 null。drainItem 第 121 行读 level.isClientSide 时抛 NPE。原版玻璃瓶走另一分支。优先修正调用方传入的世界和命中位置；复测需使用锦致装饰玻璃罐。日志没有专服进程退出证据。
- **移动结构上的门，多人联机。** latest.log 17:48:33.675；crash-2026-11-01_17.48.36-client.txt 第 18 行起。Create 0.5.1.j DoorMovingInteraction.handle 第 32 行根据门的上下半属性查相邻局部坐标，Contraption.getBlocks().get 返回 null 后无检查地取 state。Steam 'n' Rails 1.6.7 的 MixinDoorMovingInteraction 也作用于此类，其特殊门锁逻辑有独立判空。致命行是 Create 的对半门查询。日志无法区分服务端装配时漏半扇、客户端同步不完整或其他原因，也未识别具体门 ID。复现时应比对同一结构客户端与服务端两格记录，再决定是否补装配／同步修复。已有多门碰撞性能优化未覆盖此空查表路径。

结论是对报告和代码的静态诊断，未做游戏复现、未修改模组。

补核玻璃罐分支：先按手持 JarItem 的 BlockEntityTag 重建临时罐，用虚拟经验瓶真实写入临时流体槽（simulate=false），得到空瓶后从临时罐生成新物品，再处理玩家经验与换手。Moonlight 的空瓶音效分支检查 pos；成功返回仍无条件读取 world.isClientSide。若要保留原来的声音行为，应传真实 world 并保留空 pos 或显式禁用内部音效。

装配路径补核：Create 0.5.1.j 的 BlockMovementChecks.isBlockAttachedTowardsFallback 对 DoorBlock 有竖向连接判定；Contraption.moveBlock 按相邻方块朝向收集，成对、状态正确且可移动的门通常会把另一半纳入，无须额外粘胶。writeBlocksCompound / readBlocksCompound 按局部坐标传递结构表。报告不含该门 ID、两格状态或双端结构表，无法还原具体丢失环节。
