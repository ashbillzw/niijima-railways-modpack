# 新岛铁道整合包更新流程

## 1. 适用范围与当前基线

- 整合包仓库：`D:\mydata\Repositories\niijima-railways-modpack`
- 安装索引：`pack/modrinth.index.json`
- 当前开发版本：`1.6.0`；Minecraft：`1.20.1`；Forge：`47.4.6`。
- 铁道与列车相关模组是核心。更新时先检查它们与 Create 及相关附属模组的兼容性。
- 本文的数量与版本基线来自 2026-09-29 的索引读取结果，后续更新应以实际文件为准。

## 2. 下载与验证约定

1. **不要试着完整下载 mod 文件。** 当前全局代理环境可能因文件体积而下载过于缓慢。日常更新通过官方 API、版本页面及已有本地文件获取元数据；不要为获取哈希、文件大小或验证链接而自动下载完整 JAR。
2. **当一个 mod 文件在 Modrinth 和 CurseForge 上有完全相同的文件名时，假定它们是同一个文件。** 这是本项目的工作假设，不代表已经验证二进制内容相同。比较平台提供的原始文件名；如果从 URL 提取文件名，应先进行 URL 百分号解码，保留大小写、空格、版本号和后缀，不做模糊匹配。索引中的 `.disabled` 是安装目标后缀，不用于跨平台文件名比较。
3. 如果平台元数据已显示同名文件的大小或同种哈希不同，应记录冲突并暂停合并这些下载地址，交由用户决定。
4. **尽量优先使用 Modrinth 下载，仅在必要时使用 CurseForge 下载。** 先查找 Modrinth 上的目标文件并将其地址放在 `downloads` 首位；目标文件仅在 CurseForge 提供、Modrinth 地址不可用或确需备用源时，才使用或补充 CurseForge 地址。现有备用源不因单次更新而批量删除。
5. 下载明显缓慢或失败时，不反复重试。向用户提供下载链接、版本、完整文件名及建议存放目录，由用户通过更快的代理下载。
6. **当需要检查完整下载效果，或者获取这些文件时，通知用户，并准备一个目录供用户放入完整的下载、展开或运行结果。** 不把这一需要解释为 agent 自动下载的授权。具体交接方式见第 6 节。

## 3. 理解安装索引

### 顶层字段

| 字段 | 含义与更新规则 |
| --- | --- |
| `game` | 目标游戏，当前为 `minecraft`。 |
| `formatVersion` | 索引格式版本，当前为数字 `1`，不随整合包版本升级。 |
| `versionId` | 整合包版本标识，当前为 `1.6.0`。 |
| `name` | 显示名称，当前为 `新岛铁道 v1.6.0`；升级整合包版本时同步其中的版本文字。 |
| `summary` | 简介，当前为 `1.20.1, Forge 47.4.6`；不控制实际安装版本。 |
| `files` | 待下载文件数组，包含模组，也可以包含光影等资源。 |
| `dependencies` | 游戏与加载器的安装版本，当前为 Minecraft `1.20.1`、Forge `47.4.6`；不是模组间的依赖列表。 |

### 文件条目

| 字段 | 含义与更新规则 |
| --- | --- |
| `path` | 相对于 Minecraft 实例目录的目标路径。使用 `/`，不使用绝对路径或 `..` 路径跳转。 |
| `hashes.sha1` | 实际文件的 SHA-1，40 位十六进制字符串。 |
| `hashes.sha512` | 实际文件的 SHA-512，128 位十六进制字符串。 |
| `downloads` | 同一个文件的 HTTPS 下载地址数组；URL 中的空格、加号等按需要编码。 |
| `fileSize` | 实际文件字节数，为整数。 |
| `env` | 可选的客户端、服务端适用性声明；`client`、`server` 可使用 `required`、`optional`、`unsupported`。 |

**更新一个文件时，必须让目标路径、两个哈希、下载地址和文件大小共同对应选定的实际文件。** 不得只替换文件名或链接而保留旧哈希。多个下载地址是同一文件的来源，不能混入不同版本或不同加载器的文件。

当前索引的观察结果：

- 共 98 个条目：`mods/` 下 97 个，`shaderpacks/` 下 1 个。
- 每个条目都有 `path`、`hashes`、`downloads`、`fileSize`，没有显式填写 `env`；不能据此认定所有模组都适合专用服务端。
- 每个条目有 1～3 个下载地址，使用 Modrinth CDN 和 ForgeCDN。
- Distant Horizons 的目标路径以 `.jar.disabled` 结尾，下载地址指向 `.jar`。更新时保留该禁用状态，除非用户要求启用。
- JSON 可正常解析，没有重复目标路径，两个哈希的字符串格式均正确。这些检查不等于实际文件哈希校验或游戏兼容性验证。

索引之外的配置、脚本及随包文件也会影响运行结果。制作发行包时，应同时检查 `overrides`、`client-overrides`、`server-overrides` 等实际存在的目录，不能仅凭 `files` 数量判断整合包是否完整。

### 排序规则与当前观察（2026-09-29）

用户记忆中的规则是“先 Modrinth，再 CurseForge，每个部分内部按字母顺序排列”。检查时以 `downloads` 是否含 `cdn.modrinth.com` 判断来源分组：同时有两平台地址的条目归入 Modrinth 组；只有 ForgeCDN 地址的条目归入 CurseForge 组。这里的“仅 CurseForge”只描述当前索引中的来源，不表示已查证该模组未在 Modrinth 发布。

本次用不区分大小写的序数字符串比较（`.NET StringComparer.OrdinalIgnoreCase`）检查顺序，避免大小写与系统语言设置影响结果；不忽略标点，也不使用版本号的自然排序。条目序号从 `files[0]` 记为第 1 项开始。

| 检查项 | 结果 |
| --- | --- |
| 平台分组顺序 | 完全符合。第 1～77 项均含 Modrinth 地址；第 78～98 项仅含 CurseForge 地址，没有交错。 |
| 条目内的来源优先级 | 完全符合。77 个含 Modrinth 地址的条目均把该地址放在 `downloads` 首位。 |
| Modrinth 组内部排序 | 不完全符合。发现 `firstperson` 与 `notenoughanimations` 两个错位条目，详见下表。 |
| CurseForge 组按完整 `path` 排序 | 完全符合。20 个 `mods/` 条目在前，1 个 `shaderpacks/` 条目在后。 |
| CurseForge 组仅按文件名排序 | 不完全符合。最后的 Sildur 光影文件按文件名应放在 `Searchables` 与 `simpleplanes` 之间。 |

Modrinth 组内两个错位条目的正确位置：

| 当前条目序号 | 文件名 | 应处位置 |
| --- | --- | --- |
| 29 | `firstperson-forge-2.5.0-mc1.20.1.jar` | `ferritecore-6.0.1-forge.jar` 之后，`IMBlocker-5.4.5-forge+1.17-1.20.4.jar` 之前。当前误放在 `fancymenu` 前面。 |

**结论：当前不是完全有序。** 若按“平台分组 + 完整路径的字母顺序”理解，存在上述两个错位条目；若严格只比较文件名，还存在 Sildur 光影末尾放置的问题。现有布局更接近前一种规则，即同一平台分组内先按目录、再按文件名排列；这是从当前文件推断的约定。

后续更新应检查平台分组与组内顺序，将新增或更新条目放到对应位置；排序键应明确使用完整 `path` 还是纯文件名。此次只记录观察结果，未重排 `modrinth.index.json`。

## 4. 执行更新

### 步骤一：确定范围并检查现状

1. 阅读适用的 `AGENTS.md` 和本流程。
2. 查看 Git 工作区状态，保留用户已有改动，记录更新前的索引版本。
3. 明确本次要新增、升级、降级或移除的模组，以及是否变更整合包版本、Minecraft 或 Forge。不要把单个模组更新扩展为全包升级。
4. 阅读当前索引与相关配置，记录旧文件名、版本、禁用状态和下载来源。

### 步骤二：查找目标版本与依赖

1. 优先查询 Modrinth 的项目与版本元数据，确认目标为 Minecraft 1.20.1、Forge，或本次明确指定的新环境。
2. 阅读目标版本说明，检查必需前置、附属模组和已知不兼容项。不要仅凭文件名认定兼容。
3. 对 Create、铁道核心模组及其附属模组，检查相互支持的版本范围；不能默认各自最新版可以共同运行。
4. Modrinth 没有目标文件时再查询 CurseForge。跨平台文件名完全一致时，按第 2 节的假设关联来源。
5. 从平台元数据提取文件名、直接下载地址、字节数、SHA-1、SHA-512，并记录来源和检查日期。
6. 若缺少必要哈希或大小，先检查用户已提供的本地文件；仍无法取得时，进入第 6 节的用户下载交接。不得编造数据，也不要为补齐元数据自动完整下载文件。

### 步骤三：修改索引及相关文件

1. 将旧条目替换为目标版本，避免新旧版本同时留在 `mods/` 下。
2. 同步更新 `path`、`hashes.sha1`、`hashes.sha512`、`downloads`、`fileSize`。
3. Modrinth 地址优先，必要的 CurseForge 地址随后列出。新增源时应用同名假设，并注明尚未进行二进制比对。
4. 保留有意设置的 `.disabled` 后缀。不要擅自启用禁用模组。
5. 增删前置依赖前检查其他模组是否仍需要它们；按需要更新配置、脚本或资源。
6. 只有本次包含整合包版本调整时，才修改 `versionId` 和 `name`。修改游戏或加载器版本时同步 `dependencies` 与简介中的相应文字。
7. 保留原有格式和无关条目，避免全文件重排产生不必要的差异。

### 步骤四：本地静态检查

无需完整下载 mod，即可检查：

- JSON 能否正常解析，字段类型和必要字段是否正确。
- 路径是否重复，是否包含绝对路径或路径跳转，是否意外保留了旧版模组。
- SHA-1 与 SHA-512 的格式是否正确，大小是否为正整数。
- 下载数组是否非空，地址是否为 HTTPS，特殊字符是否正确编码。
- 新条目的元数据是否与所选版本相符，下载源之间是否存在已知冲突。
- 禁用状态、版本文字和游戏环境是否符合本次范围。
- 平台分组是否保持 Modrinth 在前、仅 CurseForge 在后；组内按明确的排序键检查字母顺序，含 Modrinth 来源的条目应将其地址放在首位。排序口径与历史错位见第 3 节。
- Git 差异是否仅包含预期修改。

静态检查通过后，明确报告“索引静态检查通过”。尚未验证的链接可用性、文件内容、启动及联机效果应分别说明，不能统称为全部验证通过。

### Modrinth API 查询与字段映射（YSM 测试已验证）

#### 1. 从现有索引确定项目

已有 Modrinth 下载地址的结构为：

```text
https://cdn.modrinth.com/data/{project_id}/versions/{version_id}/{filename}
```

从当前条目提取项目 ID，而不是通过模组简称猜测项目。本次 YSM 的项目 ID 为 `86xjpqqS`，旧版本 ID 为 `4aj1O0iH`。项目 ID 用于查询所有匹配版本，旧版本 ID 仅定位原来的发行文件。

#### 2. 查询匹配游戏和加载器的版本

本次实际使用的 API 为：

```text
GET https://api.modrinth.com/v2/project/86xjpqqS/version?loaders=%5B%22forge%22%5D&game_versions=%5B%221.20.1%22%5D
```

其中，`loaders` 和 `game_versions` 是经过 URL 编码的 JSON 数组，解码后分别为 `["forge"]`、`["1.20.1"]`。更新其他模组时替换项目 ID；环境参数取自索引中的 `dependencies` 或用户明确指定的目标环境。

以下 PowerShell 示例仅请求 JSON 元数据，不访问 JAR 下载地址，也不写入原项目：

```powershell
$ErrorActionPreference = 'Stop'
$projectId = '86xjpqqS'
$loadersQuery = [uri]::EscapeDataString('["forge"]')
$gameVersionsQuery = [uri]::EscapeDataString('["1.20.1"]')
$uri = "https://api.modrinth.com/v2/project/$projectId/version?loaders=$loadersQuery&game_versions=$gameVersionsQuery"
$versions = Invoke-RestMethod -Uri $uri -Headers @{
    'User-Agent' = 'Niijima-Modpack-Metadata-Check/1.0'
} -TimeoutSec 30
$candidates = @($versions | Sort-Object { [datetime]$_.date_published } -Descending)
$candidates | Select-Object -First 3 id, version_number, version_type,
    date_published, game_versions, loaders, dependencies, files, changelog |
    ConvertTo-Json -Depth 12
```

本次浏览工具无法读取此 API，改用 PowerShell 成功获得结果。若命令因沙箱网络权限被拒绝，走工具提供的权限申请后再执行；不要把权限错误误判为项目不存在，也不要反复重试下载。API 请求明显缓慢或出错时遵守第 2 节的交接规则。

#### 3. 选择版本和具体文件

- 将匹配版本按 `date_published` 降序排列，检查最新候选的 `game_versions`、`loaders`、`version_type`、`dependencies` 和 `changelog`。不按版本号字符串排序，也不直接把返回数组的第一项当成最新版本。
- 区分“最新发布版本”和“最新正式版”：用户指定正式版时筛选 `version_type = release`；若最新候选为 alpha/beta 且用户意图不清楚，用选项卡确认后再选择。本次最新匹配候选本身就是 release，无需作此选择。
- 在选定版本的 `files` 中选择实际发行 JAR，优先检查 `primary = true` 的文件，并核对文件名和目标环境。多文件或用途不明确时继续查看版本信息，不能盲目取 `files[0]`。
- API 的 `dependencies` 为空，只表示该版本元数据未列出依赖，不代表已证明与整包所有模组兼容。
- 读取返回的 `url` 即可取得下载链接；不要请求该 URL 下载完整 JAR。Modrinth 已有完整元数据时，不必为了凑备用地址再查 CurseForge。本次没有使用跨平台同名假设。

| Modrinth 返回字段 | 写入索引的字段 |
| --- | --- |
| 所选文件的 `filename` | `path = "mods/" + filename`；原条目禁用时保留 `.disabled` 后缀。 |
| 所选文件的 `hashes.sha1` | `hashes.sha1` |
| 所选文件的 `hashes.sha512` | `hashes.sha512` |
| 所选文件的 `url` | `downloads` 的首个地址；原样保留 API 返回的 URL 编码。 |
| 所选文件的 `size` | `fileSize`，单位为字节。 |

版本对象的 `id`、`version_number`、`date_published` 等用于选择和记录，不额外写成索引文件条目的自定义字段。不要把模组版本写入整合包顶层 `versionId`。

#### 4. 在临时副本中生成并验证

用户要求仅测试时，在 `D:\mydata\Agents\Minecraft相关` 下新建独立索引副本；目标文件已存在时另取文件名，避免覆盖先前结果。本次生成的是 `modrinth.index.ysm-update-test.json`。

1. 读取原索引，记录原文件 SHA-256，确认目标模组恰好匹配一个条目。
2. 只在副本中更新目标条目的路径、两个哈希、下载地址和大小。修改限定在该条目，保留其余字段、条目顺序和文本格式。
3. 解析修改前后 JSON，逐项比较：本次仍为 98 个条目，只有 YSM 发生变化，其余 97 个条目及顶层元数据不变。
4. 检查哈希格式、路径唯一性、字段类型，以及“先 Modrinth，再仅 CurseForge，各组按完整路径忽略大小写排序”。
5. 再次计算原文件 SHA-256，确认原文件未变；用 Git 状态确认原仓库没有本次产生的改动。
6. 使用 `git diff --no-index -- <原索引绝对路径> <临时索引绝对路径>` 展示差异。该命令发现差异时返回码为 1 属正常结果；无需把临时文件加入仓库。
7. 在选项卡中打开临时文件供用户检查。仅测试时不commit，也不因验证成功自动应用到原项目。

## 5. 更新记录

### 服务端 ablink 同步（2026-10-07 最终约定）

- 服务端更新器不解析 `pack/modrinth.index.json`。新增、升级、降级或移除模组时，除更新客户端索引外，还必须检查对应的服务端文件或 `.ablink`；索引更新不会自动更新服务器。
- 两服都要的模组放在 `server/shared/mods/`，仅某一服需要的放在 `server/create-cn/mods/` 或 `server/train-cn/mods/`。客户端专用模组只更新客户端索引，不向服务端加引用。
- 引用统一命名为 `实际文件名.ablink`，不使用 `__url__` 等前缀。内容以 `http://` 或 `https://` 开头时，按该直链下载文件；目标文件名只去掉 `.ablink`。例如 `memoryleakfix-forge-1.17+-1.1.5.jar.ablink` 内填写准确版本的 Modrinth 下载地址，优先使用 HTTPS。双端相同版本优先复用客户端索引的对应下载地址。
- 升降级时替换旧引用的文件名和 URL；移除模组时移除对应引用。检查 shared 与两服差异，避免同一模组的新旧版本同时存在。存在有意版本差异时保持并记录，不擅自统一。
- 没有合适下载直链的自定义或现有服务端模组可以保留实际 JAR；直接放入分包的文件也会原样复制。已有真实文件转成引用时，确认链接确实对应原版本，不猜 URL，也不为验证而完整下载 JAR。
- `.ablink` 对任意文件使用同一规则，不按 JAR、JSON 等类型增加特殊解析。目标名称由标记文件名去掉 `.ablink` 决定，不取 URL 末尾的文件名。引用先展开，再由同名实际文件或目录覆盖；shared 先于各服差异层。
- 内容不是 HTTP/HTTPS 链接时，将内容作为分支名解析（去掉可选的首尾双下划线），按部署目标相对路径引用该分支 `pack/overrides/` 下的同名文件或目录。维护时优先写 `__master__`，即使当前在 agent-dev 分支工作也以未来合入的 master 为基准；这是维护约定，不是脚本硬编码。写 `__agent-dev-1.6__` 则引用该开发分支。空内容报错。更新器 `--server` 默认 all、`--branch` 默认 master；后者仅选择服务端分包来源，不覆盖 `.ablink` 内的分支。例：`server/shared/kubejs.ablink` 内容为 `__master__`，引用 master 的 `pack/overrides/kubejs`。
- 提交前核对两服展开后的模组名称与适用范围。删除仍由 `server/delete.json` 显式指定：当前两服 mods 整目录删除重建；每项删除前询问 y/n，n 终止。需要保留额外文件时应先更新分包或删除范围。

### 更新记录内容

每次更新记录以下内容：

- 模组名称、旧版本与新版本、更新原因。
- 新增或移除的依赖，以及配置和脚本变化。
- 元数据来源、检查日期、使用的下载源。
- 哪些跨平台来源依据“文件名完全相同”进行了关联。
- 已完成的检查、待用户下载或运行验证的事项。
- 已知问题与回退所需的旧索引、配置或 Git 提交位置。

## 6. 完整下载与运行结果交接

需要实际 JAR、完整安装效果或运行验证时：

1. 通知用户具体目的，例如补齐 SHA-512、检查启动错误、验证铁道模组联动。
2. 在当前工作目录下创建独立交接目录，建议命名为 `验证交接/YYYY-MM-DD_更新主题/`。遇到同名目录时保留原内容，另建带序号的目录。
3. 按需要准备以下子目录，并在根目录写入交接说明：

   ```text
   验证交接/YYYY-MM-DD_更新主题/
     交接说明.md
     downloads/    用户下载的原始 JAR、ZIP 或整合包
     instance/     用户展开或安装后的实例，以及运行后的结果
     logs/         latest.log、崩溃报告等单独提供的诊断文件
   ```

4. 交接说明列出准确版本、文件名、下载链接、对应存放目录和需要用户执行的操作。将实际创建的绝对目录路径提供给用户。
5. 如果目标是验证整合包安装效果，请用户通过其启动器导入并完成下载，再提供安装后的实例；单纯解压 `.mrpack` 不代表索引中的远程文件已下载。
6. 用户提供结果后，在本地计算哈希和大小，检查文件布局与日志；按本次变更验证启动、入服和相关功能。运行结果不充分时明确指出尚缺的证据。
7. 不自动覆盖用户正在使用的实例，不将完整 JAR、运行缓存或日志作为更新流程的一部分提交到 Git。

## 7. 完成标准

- 索引与相关配置已完成预期修改，静态检查通过。
- 更新记录包含元数据来源、跨平台同名假设及验证范围。
- 需要完整文件或运行结果时，交接目录和说明已准备好，并已通知用户。
- 若运行验证尚未完成，将状态标为“索引更新完成，待运行验证”；只有收到并检查了相应结果后，才报告对应验证已完成。
