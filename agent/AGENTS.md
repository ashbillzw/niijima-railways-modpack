## 通用规则

### 交互与规则维护

- 面向前端的文案尽量简短精练：标题、按钮、开关和状态优先使用简短、明确的文字，避免重复解释；必要的说明放在提示或帮助中，不省略影响用户决策的关键信息。（2026-10-24 用户确认）

- 用户询问读音时，默认回答日语读音；除非用户明确另有说明，不主动补充普通话等其他语言的读音。（2026-10-13 用户确认）

- 使用中文清楚说明已完成的工作、证据、待办和限制。优先使用 Codex 的选项卡／选择题机制进行有限选项的澄清和确认，并打开相关文件或 diff 供审阅。
- 发出选项卡后给用户充分阅读和回复时间；需要其决定的工作保持等待，不因暂未回复自动选项、视为同意或开始依赖该决定的操作。
- 收到可能长期适用的新指令时，用选项卡确认是否作为长期规则；确认后写入适当规则文档。用户已明确要求记录或整理规则时直接执行，不重复询问相同授权。单次任务参数不能擅自推广为永久规则。
- 维护规则时同步本机副本和仓库副本；其他机器的副本需在拉取后比较更新，不盲目覆盖其额外规则。使用日期与具体证据处理新旧结论，不仅按文件时间选择。

- 待办集中维护于仓库 `agent/todo-list.md`，当前炼药锅 mini todo 作为明确例外独立维护并由总表链接。以后出现新的待办／改进候选／后续工作时，先用选项卡询问用户是否加入总 todo；用户明确要求记录时直接添加，不重复询问。专题保留技术依据、方案、测试步骤及历史，不另维护平行待办队列；过时内容标注替代结论与日期，不删除。（2026-10-24 用户要求）

### 独立工作区规则加载与新项目适配

- 将项目规则复制或合并到 agent 实际启动的独立工作目录根部，使用文件名 `AGENTS.md`，以便自动注入；仅放在仓库的 `agent/` 子目录不保证从其他目录启动时自动加载。已有副本先比较并保留其额外规则，接手时确认实际加载的规则来源。
- 新 agent 被要求读取本规则并适配到新项目时，应完整复制全部【通用规则】（global），同时审视【本项目规则】（project-specific）：比较旧任务与新任务的性质，识别可以迁移适用的做法，而不是一概丢弃项目规则，也不原样照搬旧项目路径、技术参数和任务状态。
- 对可适配的项目规则，可以通过选项卡逐项提出“旧项目条款 → 新项目拟采用条款”，简要说明相似性、适用范围与必要改写，请用户决定是否采用；用户确认后再写入新项目规则。用户未回复不视为同意，未获采用的项目条款不自动成为新项目约束。（2026-10-16 用户要求）
### 兼容层设计（2026-10-19 用户确认）

- 实现兼容时优先基于流体、容器等共用抽象或注册接口，避免逐项硬编码；例如需要支持水和岩浆时，应尽可能兼容液体这一抽象，而非分别增加特例。确实需要特例时先说明原因与范围；不因此擅自扩大未讨论的行为。
- 对收益较小的功能，优先沿用原生行为；若需新增整套代码，先权衡维护成本，避免为小改进增加复杂度。（2026-10-22 用户确认）

- 实现兼容功能时，先查找并尽量调用原版／依赖模组已经实现的语义入口（如喝奶使用的解效接口、容器转移接口、注册交互及配方处理器），而不是自行枚举对象、直接改NBT／状态或复制其算法。选择语义匹配且副作用合适的层级；保留适用的事件、能力、标签、返回值与取消机制。复用低层接口不等于继承所有高层Mixin，调用完整玩家操作也可能额外触发统计、进度、消耗；必须说明兼容边界。有意改变的玩法和确无合适入口的情况可保留最小适配，不为追求复用扩大行为或新增整套框架。（2026-10-24 用户要求；案例见仓库 agent/物品整合/既有语义复用审查-20261024.md）

### 阶段计时与耗时审计（2026-10-29 用户澄清）

- 按功能／做事类型划分实际工作阶段，例如资料读取与分析、方案整理、编写／修改、下载／构建、测试／验证、Git 同步／提交和等待；不是按工具调用或底层执行原理分类。聊天中简短报告阶段开始及完成，例如“编写完成，用时 1 分 0 秒”“测试完成，用时 2 分 0 秒”。没有发生的阶段不凑数。
- 在阶段边界读取真实系统时间，记录开始／结束时间、目的、完整耗时和结果，详细日志放仓库外独立工作目录的 `日志/任务耗时/`。时间戳包含日期和时区，不凭记忆或估算补造。阶段耗时覆盖从开始到完成的整个时间段，包括该阶段内的阅读、分析、编写、工具执行、结果审阅和必要的进度说明；不能只累计命令执行时间，再把大部分时间归为“未细分间隔”。
- 连续阶段按实际工作切换衔接。用户等待或独立后台等待需要时单列；并行工作注明重叠范围，不简单相加作为总耗时。工具往返、命令运行等底层细分仅在有排障需要时补充，不作为默认汇报口径，也不为计时另造复杂工程。
- 任务结束时汇总总耗时与各阶段耗时，说明最长阶段，并简短自审有无不必要或重复工作。收尾整理也归入对应阶段；确有计时遗漏时如实注明缺口，不补造数据，不将未独立测量的时间称为纯思考时间。
- 验证范围随改动风险确定；检查前说明要排除的具体问题。已有检查通过后，没有新改动、失败或异常证据，不重复运行、不扩展到无关验证。不为可逆的低影响文字修改写测试，不为计时另造复杂验证工程。日志只记任务摘要和结果，不记录凭据或敏感参数。

### Git 提交与远端操作

- 开工先检查工作区、当前分支与上游，保留已有改动；不把未提交、已提交未推送、远端已有提交混为一谈。
- 每次准备修改 Git 跟踪的项目内的项目文件前，先尝试 `git fetch`，刷新当前分支对应上游所在远端，再比较本地与上游的独有提交。只在独立工作区进行、不会改动项目内受跟踪文件的工作不适用此要求。（2026-10-16 用户要求）
- 若上游包含本地尚未拥有的提交（包括本地与远端已分叉的情况），必须用选项卡提醒用户，说明 ahead／behind、已有未提交改动及相关远端提交摘要，请用户决定先同步还是继续本地修改；不自动 pull／merge，也不因暂未回复默认继续依赖该选择的修改。用户已明确决定的同一批远端提交不重复索要相同授权，但后续修改前仍应尝试 fetch；发现新增远端提交时再次提醒。
- fetch 失败、没有远端或没有上游时，如实说明原因和当前比较依据；不能把旧的远端跟踪缓存当作最新远端状态，也不能把未能检查当作远端没有更新。权限阻止与网络失败分别处理，不擅自创建上游或执行合并。
- 首次因 `git fetch` 触发 Codex 权限审批时，直接提醒用户在审批卡中选择长期允许，并随审批请求提供 `git fetch` 命令前缀规则（`["git", "fetch"]`），减少后续重复确认。已有有效规则时直接复用；是否保存长期授权由用户在审批界面决定，不把聊天授权视为已保存。此授权仅针对 fetch，不扩展到 pull、merge、push 或全部 Git 命令；GitHub 站点放行也不能替代受保护 `.git` 目录的写入授权。（2026-10-16 用户要求）
- 适合提交时按功能和依赖关系分组，展示 diff、说明验证情况，并通过选项卡取得提交许可。删除旧资源及其替代引用等相互依赖的修改应放在同一提交，避免中间提交缺少必要内容。
- 提交前参考近期 commit message 风格；有 gitmoji 时沿用分类，必要时参考 gitmoji.dev。
- 提交身份：author 为 `chatgpt-codex-astra <me@ashbill.com>`，committer 为 `AshBill <me@ashbill.com>`。身份可通过命令级环境变量指定，不因此修改全局 Git 身份。
- 完成一轮项目工作后（包括用户要求的 commit 完成后），再自动尝试一次 `git fetch`，报告当前分支、上游、ahead／behind 及未提交改动。有可推送的本地提交且无远端新增提交时，提醒用户可以手动 push；有远端新增提交或分叉时按同步规则提醒处理，不擅自 pull／merge。fetch 失败时说明未能确认最新远端状态；仅独立工作区且不涉及 Git 项目的工作不适用。（2026-10-16 用户修订，替代“提交后选项卡询问 fetch、push”）
- **agent 不执行 push，由用户手动执行；不再在提交后弹出是否由 agent 推送的选项卡。** 本地 commit 不等于上传或部署。本规则已授权修改前及收尾时的 fetch；pull／merge 及其他改变远端状态的操作仍须按各自范围取得用户授权，不把 commit 授权扩展为远端操作授权。

### 多机器同步与冲突处理

- 用户要求同步合并时，先梳理本地未提交工作；成熟的改动优先分类展示并获准 commit，再 fetch，检查双方独有提交，再 merge。临时草稿可另议暂存；仓库外备份仅作为额外保障，不默认用 stash／恢复替代提交历史。
- 合并停在最终提交前供审阅。冲突按文件和冲突块逐项展示：共同基线、双方意图、建议方案；等用户确认后处理，不能整批默选 ours 或 theirs。
- 遇到性质完全一致的多处冲突，先说明样例和适用范围，询问本次后续同类型能否同样处理；用户同意后批量应用，例外再次讨论。这不是跨任务的永久冲突裁决。
- 自动合并也检查语义矛盾，例如已实现代码与“尚未实现”文档并存、旧目录规则与新结构冲突；实质行为差异单独讨论。
- 完成后检查冲突标记、格式及适用验证，展示汇总 diff，确认后创建合并提交。按收尾规则再次 fetch，报告提交位置、工作区状态及与上游的 ahead／behind，并提醒用户手动 push 或先处理远端新增提交；不把缓存的远端跟踪状态当作刚查询过的云端状态。

### 下载、验证与交接

- 常规使用 PATH 上的 7z 打包时，信任其基本压缩操作，以退出码及成功输出判断完成；不额外执行 ZIP 完整性测试、解压比对或逐文件哈希检查。仅在报错、有具体异常证据或用户明确要求验证时追加针对性检查。（2026-10-14 用户要求）

- 搭建测试实例等较大验证工程前，先提交包含下载内容与来源、运行方式、磁盘与具体路径、预计磁盘/内存占用及清理办法的计划，获用户批准后执行；不得将一般验证请求直接扩大为此类工程。（2026-10-12 用户确认）

- 本机使用全局 proxy。下载明显过慢或出错时，不反复重试；给出准确链接、版本、文件名及建议存放目录，让用户通过更快的代理获取，再继续本地验证。权限阻止与真实网络失败应区分处理。
- 不默认给 yt-dlp 添加 cookies；需要认证时按当前任务单独处理。凭据、cookies 和令牌不得写入仓库或交接报告。
- 区分“本地处理完成”“静态检查通过”“实际运行验证通过”“已部署上线”。没有证据不宣称后续状态；后台进程已启动不等于已完成。
- 对未来 agent 有用的结论必须在任务结束前写入仓库合适的专题文档或 handoff，不只留在聊天或本机日志。记录日期、适用条件、验证结果、路径和剩余事项；过时记录注明范围与替代结论。

### 新增模组候选清单展示格式（2026-10-12 用户确认）

- 生成或重新展示待新增模组清单时，沿用用户指定的完整逐项表格格式，不将多个模组合并进同一行。
- 开头说明当前具名候选数量与待选型需求数量，并说明“候选不代表已经决定安装”；数量随最新状态计算，不固定为历史的 20 项与 2 项。
- 具名候选按类别分组，使用三列：`编号 | 候选 Mod | 当前需要讨论的重点`。每个模组单独一行，编号跨类别连续；分类可沿用基础机制、地图、食物与生活、机械动力与交通、建筑与展示、服务器工具，并按实际内容调整。

- 维护前读 `agent/服务端/YSM模型与包服差异.md`、`agent/服务端/服务端更新器.md`。`server/` 当前是 shared 共享层和两服差异层，不是完整运行实例。
- 共用 KJS／YSM 从包内资源维护，通过 shared 的 `.ablink` 引用；额外模型和单服差异按专题规则保留。实例配置与实际存档 `serverconfig` 按适用范围同步；改 `defaultconfigs` 不等于改已有世界。
