## 当前方向：长期反馈页与活动页分离（2026-11-06 补充）

用户明确反馈界面应长期保留，能够单独打开；本次活动只是临时嵌入／复用它。活动结束不下线反馈页，也不将通用反馈流程写死到 v1.6 活动中。活动页负责活动介绍、期限和奖励说明等活动内容，反馈页负责 Bug／功能建议表单与附件提交；尚未确定的期限、奖励值不自行填写。下节初轮构想中的活动标题与风格适用于活动页面，不意味着永久反馈页必须一直使用同一活动标题。

用户提出可以用 iframe 嵌入。该方式可行，优先考虑同源部署：长期反馈页有独立地址，活动页以 iframe 加载相同页面，不维护两套表单。iframe 是候选技术方案，并非已选定或已在 FM／MCEF 中验证；实施时需确认页面允许被活动页嵌入、布局高度以及游戏内文件选择／剪贴板能力，不能假定 FM 的顶层桥接对象会自动出现在子 frame。也可在同一前端复用表单组件，最终方式后续确定。依据：[MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)、[frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors)。

### 启动器自定义崩溃界面提议

用户提出在游戏非正常退出后显示 custom crash screen，提供两个操作：

| 按钮 | 用户提出的行为 |
|---|---|
| 保存错误报告 | 汇总本次启动相关日志和诊断文件，保存成类似 PCL 的 ZIP |
| 打开反馈界面 | 打开上述长期保留的反馈页面 |

应由仍在运行的启动器显示此界面，因为游戏进程此时已退出；不是依赖游戏内 Screen 在崩溃后继续工作。非正常退出的具体判定及主动终止游戏如何处理仍需结合 Prism 既有流程确定，正常退出不作为目标触发场景。记录的两个按钮文字来自用户；完整错误文字、位置和触发规则按既有约定在实际接入前确认。本轮仅记录提议，未实现或单列新的崩溃页待办。

现有 Prism “上传日志”是玩家主动点击并经过确认后上传到所配置的服务，默认具备能力不代表崩溃后自动上传。新提议的“保存错误报告”是本地导出；“打开反馈界面”也不代表自动上传附件、自动读取本地日志或预先填入本地路径。文件如何交给网页、诊断包收集范围及敏感信息过滤后续讨论，不能把按钮文字扩展为未授权的传输行为。

## 日志文件方案讨论

静态前端可以选择文件并向已有服务器上传；“静态网页”并不等于只能展示文字。但浏览器选中文件后只取得本机文件访问权，若要让腐竹收到文件，仍要通过 QQ 等既有渠道或上传接收端传输，复制正文不会顺便发送附件。普通网页应由用户选择文件，不能凭已知路径直接读取玩家的 `latest.log`。依据：[MDN 文件选择](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file)、[文件上传](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Forms/Sending_and_retrieving_form_data)。

| 方案 | 玩家操作 | 额外服务与取舍 |
|---|---|---|
| 静态页＋QQ 附件 | 填写并复制正文，发给腐竹；另把日志文件发到同一个 QQ 对话 | 最简单，不新增上传服务；正文与附件需要两次发送 |
| 静态页＋现有 copyparty 收件目录 | 表单选择日志并上传，复制的反馈正文附带文件标识／相对路径；腐竹登录取附件 | 能保留自定义活动页，无须新写反馈业务后台；需要配置上传权限、容量限制及浏览器访问 |
| 独立反馈后台 | 正文与附件一并提交，后台集中管理 | 适合需要自动收件、查状态和长期管理时；当前尚未要求这些功能，不建议第一版就扩大至此 |

初轮建议（历史）：若希望附件也在网页完成，优先考虑第二种；若希望最快上线且完全不调整服务器，第一种仍可行。用户后续提出正文与附件一起提交，见下节；不再把“复制后发 QQ”视为 copyparty 方案的必要步骤。

### 使用现有 copyparty 的拟议方式

这是拟议配置，不是当前服务器状态：为反馈附件设置独立收件目录，玩家可上传但不能浏览或下载其他人的日志，腐竹有读取权限；上传成功后正文记录文件标识，供腐竹查找，不要求向公众开放日志直链。文件大小、上传频率和容量上限由服务端限制，具体值后续决定。copyparty 官方文档支持写入与读取权限分离、仅上传目录，以及相应的上传限制：[权限说明](https://github.com/9001/copyparty#accounts-and-volumes)、[上传规则](https://github.com/9001/copyparty#upload-rules)。

活动页和上传接口优先安排在同源路径；若跨域，再核对 CORS 和认证配置。上传目录与页面实际 URL 均未确定。前端不能放管理员密码或其他私密凭据。日志可能含聊天与服务器地址，收件目录不默认公开浏览。上述边界与日志收集直接相关，不扩大为全站改造。

### 后续讨论：正文与附件一并提交、匿名仅收件（2026-11-06）

用户进一步提出：既然已有 copyparty，前端能否将反馈信息和日志合并上传；同时要求讨论一个无需凭证、只可上传不可读取，限制单文件大小及整个目录总量、满额拒收的独立目录。本轮仍只讨论与记录，未创建收件目录或改服务器配置。

澄清：前文“复制到剪贴板”只指正文及附件编号，不是将整个日志序列化或 Base64 后放进剪贴板。用户并未要求这种大文本传输方式。

可行的收件设计：前端将标题、详情、反馈类型等表单数据生成 `feedback.json`（也可选择易读的文本格式），与玩家选择的日志文件一起生成一个 ZIP，通过 copyparty 的上传接口提交。一个反馈对应一个带随机标识的文件，避免正文和附件分开上传造成配对困难。无需先让玩家把 ZIP 下载到本机再手动上传。生成 ZIP 需引入合适的前端库，例如 [JSZip 的 Blob 输出](https://stuk.github.io/jszip/documentation/api_jszip/generate_async.html)；文件保持二进制，不需要 Base64。大文件仍占浏览器内存，应限制所选原始文件总量，见 [JSZip 限制](https://stuk.github.io/jszip/documentation/limitations.html)。

如果采用上述设计，前端仍是静态页面，copyparty 已经承担存储服务，足以提供“填写并提交完整反馈”的收件功能。QQ 可成为可选联系渠道。此前表格把“正文与附件一起提交”只归于独立后台不够准确：真正额外的业务是反馈列表、处理状态、回复、通知和发奖记录等；copyparty 不会自动把上传包解析成这些业务记录，但未来可以按需要继续设计，不代表必须立即另写服务。

copyparty 配置示意（未部署；数值为讨论例子，管理账号需使用已有配置）：

```ini
[/feedback-inbox]
  /srv/copyparty/feedback-inbox
  accs:
    w: *
    rw: ashbill
  flags:
    e2ds
    sz: 1b-11m
    vmaxb: 2g
    vmaxn: 2000
    df: 4g
    nosub
```

- `w: *` 允许匿名上传；不给匿名用户 `r`、`g`、`G` 等读取权限，不能通过文件名直链绕过读取限制。公开活动页必须放在另一个可读目录；收件目录不要再经其他公开挂载或静态路径暴露。
- `sz` 已按用户最新确认同步为每个上传 ZIP 1 B～**11 MiB**，替代早期 20 MiB 示例；`vmaxb` 将收件卷总量限制为 2 GiB，`vmaxn` 限制文件数量；`e2ds` 是总量与数量统计所需的索引条件。总量等示例仍需在后续服务器配置时核对。
- `df` 在磁盘空闲空间不足时拒收，`nosub` 禁止上传到子目录。若后来添加每 IP 频率／流量限制，官方说明 `maxn`／`maxb` 按默认单进程 `-j 1` 计算，多进程会改变实际限额；示例未自行确定这些策略。
- 如果“仅收件”也要求禁止上传者撤回，实施时另核对 `unpost`：上游默认允许一定时间内撤回自己上传的文件，不能仅因没有 `d` 权限就宣称不可撤回。本轮未改全局配置。

配置依据：[官方权限与卷](https://github.com/9001/copyparty#accounts-and-volumes)、[上传限额](https://github.com/9001/copyparty#upload-rules)、[上传撤回](https://github.com/9001/copyparty#unpost)。这些结论针对本次查阅的上游文档，用户服务器部署版本尚未核对。

磁盘边界：`vmaxb` 是应用层容量限制，不等于文件系统硬配额。上游 `Lim.chk_vsz` 会按已统计容量及当前文件大小拒收；`up2k._get_volsize` 也计入登记中的上传任务。但普通 HTTP 上传路径存在文件写入后的容量复核和失败清理，索引、服务日志、临时文件及并发在途占用不能只靠该数值作硬保证。若要求即使遭恶意上传也不能占满宿主磁盘，建议将收件目录放在有文件系统／存储卷配额的独立空间，再叠加上述应用限额；具体配额方式取决于实际 NAS／服务器环境。依据：[authsrv.py](https://github.com/9001/copyparty/blob/hovudstraum/copyparty/authsrv.py)、[up2k.py](https://github.com/9001/copyparty/blob/hovudstraum/copyparty/up2k.py)、[httpcli.py](https://github.com/9001/copyparty/blob/hovudstraum/copyparty/httpcli.py)。这是防塞满磁盘的建议，未实施或验证攻击场景。

## 游戏内可行性与已核对证据

### 复制剪贴板

2026-11-06 本机 `build/pack-test.zip` 的文件清单包含 FancyMenu 3.7.0 与 MCEF 2.1.6；仅读取目录记录和既有本地 JAR，未下载新 JAR、未运行游戏。

- FancyMenu 官方 3.7.0 更新记录明确加入从 Browser 元素执行 FM 动作的能力，见[官方 changelog 的 3.7.0 节](https://github.com/Keksuccino/FancyMenu/blob/master/changelog.txt)。
- 对本机 3.7.0 JAR 的 `de.keksuccino.fancymenu.util.mcef.ActionBridge` 进行字节码检查，确认注入 `window.fancymenu.execute(...)`、`executeWithCallback(...)` 和 `fancymenu-ready` 事件。
- 同版本 `CopyToClipboardAction` 的标识是 `copytoclipboard`，执行时调用 Minecraft 的 KeyboardHandler 剪贴板入口。
- 因此游戏内网页可以优先采用既有 FM 桥接路径复制文本，无需先新增自研桥接模组。当前版本可按 `fancymenu.execute('copytoclipboard', text)` 设计；须等待桥接就绪，并核对动作回调、中文、多行文本及 QQ 粘贴结果。
- 当前官网示例主要是更新版本的 `fancymenu.actions.execute(...)`，不能直接假定 3.7.0 也具有该命名空间。参考[最新浏览器 API](https://docs.fancymenu.net/docs/en-US/browser-api)时应以本机版本为准。
- 普通浏览器采用 HTTPS 下的 `navigator.clipboard.writeText()`，由用户点击触发；权限与浏览器限制仍要处理。依据：[MDN writeText](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText)。

结论是“存在已有实现路径”，不是“已在游戏中验证成功”。

### 游戏内选择日志文件

普通浏览器有标准文件选择控件。当前 MCEF JAR 包含 JCEF 文件对话框接口，但接口存在并不证明 FM 画面中的系统文件选择器、取消行为、中文路径和文件上传均正常；本轮不把它们写成已验证能力。

#### 共用消息输出 API（2026-11-06 用户要求，尚未实现）

为需要向玩家输出信息的功能提供统一入口，集中处理在线输出与离线转邮件，业务代码不重复编写“如果玩家不在线则转邮件”。接口命名和实现类尚未指定，以下只确定语义：

| 调用与状态 | 行为 |
| --- | --- |
| 普通消息输出，玩家在线 | 正常向该玩家输出消息，不因开启离线转邮件就额外发送一封邮件 |
| 普通消息输出，玩家离线，`离线转邮件 = true` | 由共用 API 自动将该消息转为 Inbox 系统邮件 |
| 普通消息输出，玩家离线，`离线转邮件 = false` | 不自动转邮件；不擅自增加登录后聊天补发 |
| 直接发送邮件 | 使用独立邮件入口；无论玩家是否在线，语义都是投递邮件，不等同于普通消息的离线兜底 |

美团下单人的成功／超时失败结果使用允许离线转邮件的普通消息语义；具体离线交付**等待 Inbox 安装后实现**，不把“持久化后登录补发聊天”当作用户已选择的替代方案。邮件标题、发件人、正文映射及不可用时的处理，在接入真实 API 时确定；本轮不编造 Inbox 已有的 Java 签名或功能。

调用方复用共用输出入口，直接邮件仍保留独立调用路径；两者均属于系统／管理员能力，不因此开放玩家互发。该设计是本项目功能记录，尚未写入或改造 TrainResync 代码。
