## 一、完整机制整理

### 1. 命令与订单生命周期

本轮以用户实际流程中的`/meituan`前缀统一命名。此前`/diancan`、`/jiedan`、`/songda`仅作讨论时的简写，不据此注册顶层命令；更早的`/meituan xiadan`是否保留别名未定。

| 命令 | 用途 |
| --- | --- |
| `/meituan diancan` | 创建待接点餐，或更新自己现有待接点餐的位置 |
| `/meituan quxiaodiancan` | 取消自己仍在玩家待接池中的点餐 |
| `/meituan jiedan` | 从两张待接表稳定抽取至多5单；动物单补位随近24小时完成数衰减，0单时提示无单 |
| `/meituan jiedan <id>` | 接取列表中指定订单；正式接取时锁定该预览的内容 |
| `/meituan songda` | 核对距离和整单物品，成功后交付并发放报酬 |

**所有美团功能仅能在主世界使用。** 玩家在其他维度执行这些命令时，聊天栏统一提示`【美团】只能在主世界送餐！`，不创建、修改或接取订单，也不执行交付。此规则不仅针对`/meituan songda`。

玩家单生命周期：**待接点餐 → 列表预览（仍在待接池）→ 正式接取并移出池 → 成功送达／超时失败**。待接阶段可取消；已接取后不可取消，不区分下单人或配送员。

动物单由系统生成并进入动物待接表，带5–30分钟的待接有效期；正式接取后移出待接表，进入独立配送状态。待接过期与接单后的200分钟配送超时是两件事，不沿用动物单剩余待接时间作为配送期限。不生成下单生物。

### 2. 距离、超时与配置基准

| 项目 | 当前设计 |
| --- | --- |
| 每单食品种类 | 1–3种 |
| 每种基础数量 | 3–7个，再乘该物品数量乘数；留空按1 |
| 列表中的玩家单 | 至多3单，不受动物补位衰减限制；列表总数至多5单，允许少于5单 |
| 动物待接表 | 每位接单者按需维护一份；拉取时清除过期项，再补足至5项；单项待接有效期随机5–30分钟 |
| 动物单补位目标 | `T = max(min(7 − N, 5), 0)`；N为当前查看者近24小时成功完成的订单数 |
| 普通动物单范围 | 执行查看列表者周围XZ半径500格，可配置 |
| 远动物单范围 | XZ距离500–1000格环带；发生概率**0.25**，概率和起始距离可配置，终点1000为当前设计值 |
| 远单收益乘数 | **×1.5**；玩家单按实际XZ距离，超过远单档起始距离时也适用，不受随机单最远距离限制 |
| 玩家单收益乘数 | **×1.5** |
| 火爆加成 | 整单首次预览时以**0.05**概率触发；触发后从**1.50–2.00**按**0.01**等概率抽取，缓存后不重掷；参数可配置 |
| 食品固定加成 | 按物品在JSON中配置任意名称与乘数，例如新品；不限制为固定列名 |
| 送达半径 | **XYZ三维距离10格**，暂定，可配置 |
| 配送超时 | 正式接单后**12,000秒＝200分钟＝3小时20分钟**，后续可配置 |
| 配送员同时接单数 | 最多1个未完成订单 |
| 点餐者池内单数 | 最多1个待接点餐；已接走的订单不占池内名额 |

**两种距离不得混用：**

- 列表显示、随机XZ范围、远单资格：`sqrt((x₂−x₁)² + (z₂−z₁)²)`，不计Y。
- `/meituan songda`：`sqrt((x₂−x₁)² + (y₂−y₁)² + (z₂−z₁)²)`，需要进入配送XYZ的10格球形范围。上下高差同样影响是否能交付。

十个标准Minecraft昼夜周期按`10 × 20分钟`换算，作为超时秒数的默认值。睡觉跳夜、修改世界日历不跳过配送时限。用户最新确认**离线计时、停服暂停**：使用服务器累计运行毫秒数，保存累计值及已接订单截止点；重启后继续剩余时间，不重新给满200分钟。

### 3. 玩家点餐：落点、待接池与更新

#### 3.1 选择放箱位置

执行`/meituan diancan`时，以玩家**腿部所在方块**为起点，依次检查：

1. 当前腿部格是否为air。
2. 若不是，检查同Y层周围的另外8格。
3. 若仍未找到，检查上方一层对应3×3的9格。
4. 任一阶段找到air即选中；全部失败则提示`【美团】外卖箱放置空间不足！`。

选中格的实际XYZ才是下单位置；选到旁边或上方时不能继续使用原玩家坐标。邻格内部遍历顺序未定。更新位置时新落点失败是否保留旧单，见末尾未覆盖项。

#### 3.2 玩家待接池只保存点餐请求

- 点餐时**不决定、不显示餐品内容**，池中记录下单人身份与位置；订单内容延后到列表展示时生成。
- 每人池内至多一条。重复`/meituan diancan`直接更新现有待接请求的位置，不另外注册一条，也不修改已接取的订单。
- 玩家待接表的总条目数不设本轮上限，可以有任意数量的不同玩家点餐；“每人一条”不是“整张表一条”。表内新增、移除条目会触发列表重新随机排序；只更新XYZ不触发重排。
- 待接请求及其定位标记状态需持久化：下单人登出、服务器停服再开服后，请求仍在；下单人登录后重新看到标记。
- `/meituan quxiaodiancan`只删除池内待接请求，并停止其定位粒子。不存在待接请求时不能取消已送货中的单。
- 正式接取瞬间将请求移出玩家池、绑定配送员，并锁定该预览的餐品、数量、收益及目的地；显示预览不等于接取。
- 请求被接走后，单主可再发起一条待接请求，与旧配送单并存；单主可能同时有多个被不同配送员接走的配送中订单。
- 拉取候选时直接排除下单人自己的单，不让它出现在自己的选单中，也不设计“不能接自己的订单”提示。接取校验仍须保证订单归属有效，不能因列表过滤就信任过期快照。每位配送员最多持有一张未完成订单。

### 4. 点餐广播与单主通知

点餐成功后，向满足下列任一条件的其他在线玩家广播：

- 近7个自然日内没有收到过这类广播；**或**
- 近7个自然日内至少成功完成过一次订单。

这是**或**关系。近期完成过订单的玩家不会因为刚收到一次广播就被第一条过滤掉；本轮不将其改成全体玩家七天限一次。用户确认广播文字为`【美团】收到{玩家}的点餐订单！接单：/meituan jiedan。`。重复更新位置是否再广播及自然日边界仍待确定。

有人正式接取玩家单时，通知单主配送员姓名。送达成功或超时失败时，通知单主对应结果；**这两类结果通知若单主不在线，转入邮件**。用户最新决定：离线交付先记录，等待Inbox安装后实现；已将Inbox登记到[待新增模组](../模组管理/待新增模组.md)，不采用此前提出的“登录后补发聊天”替代方案。

用户要求建立完整的**共用消息输出API**：含一个“离线转邮件”布尔参数，为true且目标玩家不在线时，由API统一转换为系统邮件；在线时正常输出。各功能复用此入口，避免重复判断玩家是否在线。**直接发送邮件使用独立逻辑**，不以在线状态切换成聊天。详细语义记录于[邮件专题](活动网页与反馈收集初步构想.md#游戏内邮件系统可能性2026-11-06)；当前尚未安装Inbox或实现此API。

成功通知不区分放箱成功或直接掉落物品，统一采用用户提供的外卖送达文本。下单成功、接单提示等文本可带`（N 单 送货中）`前缀；用户已给出N＝1的示例，其余状态的完整格式尚待补齐。

### 5. 餐品生成、数量与收益

#### 5.1 在展示时生成，接取时锁定

用户审阅后确认：**首次形成可见预览时生成餐品和收益，正式接取时锁定同一份内容**。玩家待接表仍不在点餐时生成餐品；动物待接表在补入新项时调用随机生成流程。不得在玩家看完列表再接取时重掷餐品或价格。

2026-11-06后续补充：相同表版本下反复拉取不能靠重掷随机数刷新餐品或列表。预览内容与待接请求分开维护；接取前用列表标记校验，已失效则提示变化并重新展示，不自动接取新列表中的同号订单。动物池按每位接单者分别维护；玩家单仅改XYZ且远单资格改变时，只重算并重展示，不能重新生成餐品，见第6节。

#### 5.2 数量乘数

每单随机1–3种食品，每种基础数量随机3–7个，再分别乘该食品数量乘数。空白按1。例如切片倍率4，基础数量6，则要求24片。种类数不再乘入每种数量。

保留少量非食品订单的早期方向，实际候选及倍率待审核。特殊NBT物品不以相同ID冒充普通订单物品。价格表仍为待游戏内审核的草稿，本轮不改价。

#### 5.3 收益和显示乘数

依据物品单价、最终需求数量及本单实际适用的价格乘数计算总收益。数量乘数已反映在最终数量里，不能再作为价格乘数重复相乘。只展示本单active的加成；按当前模拟流程作为收益明细显示，不自行增加玩家手动勾选乘数的功能。

**用户已确认：只在最终总收益处向下取整，中间不取整。**

- `floor(123 × 1.5 × 1.5) = floor(276.75) = 276`。
- `floor(123 × 1.5) = floor(184.5) = 184`。

因此原例的整数结果保留，但算式需明确`floor`，不能把未取整的乘积直接写成整数等式。对多食品订单也只在整单最终金额取整，避免逐项截断。

2026-11-06最新确认：**玩家单×1.5；远单收益×1.5；火爆概率0.05，触发时随机倍率1.50–2.00；远动物单生成概率0.25**。火爆不再默认关闭。玩家单按实际XZ距离计算，超过远单档下限也可叠加远单乘数；不因超过系统随机落点范围就排除玩家单。

用户已确认：**火爆按整单在首次预览时抽取一次**，触发后从1.50、1.51、……、2.00共51个值中等概率取倍率并缓存。重复查看、跨远单分界重新计价都沿用该结果，不能靠刷新重掷；未触发也缓存该结果，不在后续查看中再次尝试触发。

游戏文案暂沿用用户写的“元”；内部表中的“币”指同一货币计价，不另建兑换比例。列表可做颜色区分；**叠加收益乘数合算严格大于×2时，总收益加粗并标紫**，这是用户提出的展示方案。其余颜色尚未指定。

#### 5.4 食品JSON结构

用户希望采用“物品 → 价格＋加成映射”的结构；`加成`下可以直接添加`新品`或其他自定义名称，不需要每增加一种固定加成就新增硬编码字段。`数量乘数`单独维护，用于需求数量，不是收益加成。

下面以物品注册ID作为键，将用户给出的结构具体化；已用于统一`config/trainresync.json`的`meituan.foods`字段。前三种测试食品各16币，示例中的“价格3”不覆盖已确认价格。未指定的固定加成留空，不默认给全部派添加新品加成。

```json
{
  "farmersdelight:apple_pie": {
    "价格": 16,
    "数量乘数": 1,
    "加成": {}
  },
  "farmersdelight:sweet_berry_cheesecake": {
    "价格": 16,
    "数量乘数": 1,
    "加成": {}
  },
  "farmersdelight:chocolate_pie": {
    "价格": 16,
    "数量乘数": 1,
    "加成": {}
  }
}
```

例如某项要加新品及另一种固定加成，可将它的`加成`改成`{"新品": 1.5, "某个啥加成": 1.5}`；这里只演示结构，未指定哪件物品启用。价格按单个库存物品计，数量乘数缺省为1。

对于物品i：`最终数量ᵢ = 随机基础数量ᵢ × 数量乘数ᵢ`，`餐品小计ᵢ = 价格ᵢ × 最终数量ᵢ × 该物品各固定加成之积`。整单先合计各餐品小计，再乘实际适用的订单条件加成，最后统一向下取整；不同食品各自的新品等加成不能误乘到整单的其他食品上。火爆、玩家单和远单加成位于订单条件层，火爆结果按已确认的整单首次预览抽取规则缓存。

### 6. 双待接表、稳定列表与接取校验

#### 6.1 两张待接表

1. **玩家待接表：** 全服玩家点餐请求的集合，总量可以任意多；每位玩家至多一条。新增、取消、被接走属于增减；单纯修改下单XYZ不算排序意义上的表变化。
2. **动物待接表：** 每位接单者按需维护一份，保存该玩家的系统随机待接项；每次拉取自己的表前按时间戳清理并补齐至5项。列表只取其中需要的数量，不因用户少取了几项就删掉剩余有效项。别人动物池的增减不改变自己的排序依据。

正式接取后，订单离开其待接表，进入已经绑定配送员的状态，不继续占用待接名额。玩家单的接取移除已有明确约定；动物单按同一“待接／配送中”区分处理，不能把同一待接项反复领取。

**2026-11-06后续确认：** 用户明确采用每位接单者独立动物池。当前约10名活跃玩家、每人5项，仅50条动物待接记录；本设计采用“全服玩家待接表＋各接单者个人动物待接表”。此前静态分析仅支持数据规模合理，不表示地形搜索已性能实测通过。

新动物项围绕该接单者**生成该项时**的位置生成并缓存目的地，因此展示列表时就能计算距离与收益，正式接取时不用再生成坐标。只移动查看者不会重掷已有动物项或改变其目的地；移动后距离可以变化，旧项不保证仍在新位置周围500格内。离线缓存回收、动物池跨重启恢复需与稳定列表约定一起确定，不能默认每次重登清空来刷新订单。

共享池也不一定要等接单才生成位置：可以共享餐品模板，在列表展示时为每位查看者生成并缓存坐标。但这样仍需个人预览状态，省下的记录有限，却增加模板与个人坐标的关系管理；本轮不采用此复杂度。

#### 6.1.1 开销分析范围

- **缓存和检查：** 10名实际持有个人动物池的玩家约50项，100名约500项。每次维护个人池只需对最多5项比较到期时间；无逐tick遍历。条目含名称、少量餐品、数量、坐标和时间戳即可，不为待接订单创建生物或强制常驻区块。
- **主要成本是落点搜索：** 本机原版1.20.1主世界`min_y=-64`、`height=384`。若逐格向下扫描，单人一次补满5项的保守上界为`5 × 65 × 384 = 124,800`次方块检查；10人同时全补可达1,248,000次。已有有效项不必重找坐标；多数查找可提前命中，这里不是典型耗时或实测次数。
- **不能只看检查次数：** 未加载区块的读取、尤其未生成区域的地形生成，可能比订单记录和随机排序重得多。只保存坐标不需要让这些区块一直加载。
- **实现阶段再验证：** 应控制一次处理的地形搜索工作量，避免把所有补单与区块工作无界地堆在同一tick；具体调度、是否允许新地形生成及其体验需另定。不能为优化而悄悄限制到已加载区块或更改65次落点规则。
- 尚无Java对象布局、实际保存格式或运行基准，不编造KB／毫秒数字，也不保证整次生成零卡顿。此处结论仅支持个人订单池的数据规模选择。

#### 6.2 动物表按拉取惰性过期

每次拉取动物表时，顺序固定：

1. 检查表内每一项的到期时间戳，删除已经timeout的项。
2. 保留其余有效项及原来的到期时间，不因读取续期。
3. 若不足5项，继续调用随机生成流程补项，直到正好5项。
4. 每个新项在生成时随机确定5–30分钟（300–1800秒）的待接有效期，记录`expiresAt = generatedAt + 有效期`。
5. 完成清理、补齐后，再从该表拉取候选。

存静态时间戳，**不每tick遍历或倒数**；过期清理发生在拉取时。有效期的随机分布和时间戳具体单位未指定。即使无人查看时条目已经过期，也只在下次读取时清理，不需要主动后台扫描。

本节只规定动物待接表的5–30分钟过期，不替代已经接取订单的12,000秒配送时限。

#### 6.3 玩家单优先，动物补位随完成数衰减

每次查看以当前玩家为对象：

- `N`：近24小时内成功完成的订单数；采用滚动24小时窗口，不是零点重置的自然日计数。按目前“完成单数”的原意计成功完成，失败／取消不计；尚未指定只统计动物单。
- `P`：从玩家待接表中拉出的可接玩家单数量，排除自己的单，范围0–3。
- `T = max(min(7 − N, 5), 0)`：用动物单补足的目标总数。
- `A = max(T − P, 0)`：从动物表补入的数量。
- 最终显示数量`L = P + A = max(P, T)`，范围0–5。

先取至多3张玩家单；只有当前数量不足T时，才用动物单补差额。T小于P时保留全部P张玩家单，不截掉玩家单。因此完成单数越多，只会减少动物单补位机会，不使现有玩家单消失。

| 近24小时成功单数N | 目标总数T | 有3张可接玩家单时补动物单A | 没有可接玩家单时补动物单A |
| --- | --- | --- | --- |
| 0–2 | 5 | 2 | 5 |
| 3 | 4 | 1 | 4 |
| 4 | 3 | 0 | 3 |
| 5 | 2 | 0（仍显示3张玩家单） | 2 |
| 6 | 1 | 0（仍显示3张玩家单） | 1 |
| ≥7 | 0 | 0（仍显示3张玩家单） | 0 |

最终L＝0时提示“无单”。这不是每天最多完成7单的硬上限，玩家单仍可继续提供；也不是动物表缩小到T项，动物表在被拉取并维护后仍补足5项。

#### 6.4 随机但稳定的顺序

- 顺序需要随机，但随机结果以两张表的状态为依据，而不是每次`/meituan jiedan`重新洗牌。
- 全服玩家待接表发生增减，或当前查看者自己的动物待接表因过期／补项／接走而发生增减时，更新排序依据并随机重排；其他人的动物池变化不影响该查看者。
- 两张表均未发生上述变化时，对同一查看者保持相同的候选顺序及编号；只更新玩家单XYZ不重排。
- 新顺序可能恰好与旧顺序相同；“重新随机”不保证每一次都换位置。
- 同一表版本下的餐品预览也应稳定，避免编号稳定却内容反复重掷。
- 排序本身的稳定不意味着所有显示值冻结：查看者移动会改变距离；滚动24小时计数因完成订单或旧记录移出窗口而改变时，T和显示条数也会变化，但不应因此重新随机排列底层候选。

可使用基于表成员／版本的稳定随机种子或缓存结果实现；这里确定行为，不指定hash算法。

执行`/meituan jiedan <id>`时，不能按当前列表的第id项直接接单，必须先核对用户看到的那一份快照：

1. 核对全服玩家待接表及当前接单者自己的动物待接表；涉及动物表时，在必要的读取中按前述规则检查到期项，不能只因无人tick清理就把过期项视为有效。
2. 若相对展示时表成员已经变化，则本次不接取任何订单，提示“选单发生变化”，并按新表状态重新拉取、展示列表。
3. 玩家需依据新列表重新选择；不能自动把旧数字套到新列表上继续接取。
4. 表状态与快照仍一致时，按快照中的具体订单身份接取并锁定其预览，不只按位置编号识别。

具体提示全文尚未指定；本轮记录触发条件和提示含义，不代写已确认的玩家文案。

**2026-11-06用户明确：单主更新玩家单XYZ，或接单者自己移动时，都按是否跨过远单分界处理。** 以下针对接取前、表成员本身没有增减的情况；实际距离始终用XZ二维：

| 单主改XYZ或接单者移动后的结果 | 选单处理 |

### 7. 动物单配送位置

在当前接单者的个人动物池生成新项时，以该玩家当时的位置为中心，在普通XZ圆形范围或远单环带中抽取XZ，再确定并缓存Y。列表直接显示此目的地相对查看者的XZ距离，不延迟到正式接单才生成位置。已有有效项不因反复查看或玩家移动而重选地点。玩家单直接使用既有下单位置，不走本算法。

每次从主世界build height顶部向下，找到该XZ的**最高非空气格**后判断；若不符合本轮条件，则重抽XZ，不能继续往下找另一个方块替代。

| 尝试次数（从1开始） | 接受条件 |
| --- | --- |
| 第1–32次 | 最高非空气格为solid |
| 第33–64次 | 放宽接受non-solid，但排除fluid |
| 第65次 | 最后一次，接受任何非air方块或fluid，必须给出落点 |

接受时，配送位置是该格上方一格。若整列直到底部仍全是air，按用户原话放在“最低一格虚空的上面”。具体最低Y、最高地表上方越界，以及solid／fluid的程序判定尚待确认。第65次为兜底，不再有第66次。

定位标记使用**`minecraft:end_rod`白色末地烛粒子**，悬浮于配送点附近；持续效果通过重复发出粒子维持，不生成实体生物。

| --- | --- |

### 9. 交付：检查、扣物、放入世界

#### 9.1 `/meituan songda`的检查顺序

1. 玩家应有正在配送的订单；无单时的提示尚未提供。
2. 判断玩家到订单XYZ的**三维距离是否在暂定10格半径内**；不满足则提示过远，附目的地XYZ，不扣物。
3. 核对物品栏是否有整单要求的完全相同物品及足够数量；不足或特殊NBT不匹配则提示餐品不足，不扣任何一项。
4. 全部满足才一次性完整扣除整个订单，再进入对应交付分支。

不能先扣部分物品再发现缺货。距离过远或缺货只是这次命令未能交付，订单继续有效，不能直接当成终止失败；接单后以自然超时作为失败终点。

#### 9.2 玩家单

扣除成功后，在锁定的下单XYZ尝试生成箱子，将该单物品放入。若地点已不满足放箱的空位条件，直接在同一XYZ生成对应掉落物，不重新找落点。

原句“不再为air且无fluid了”的流体分支尚有歧义，暂记作占位后掉落兜底；能否直接在流体处放箱需确认。不会擅自删除占位方块或覆盖已有箱子。箱子容量不足或其他放箱失败怎么处理，仍待补齐。

**正常放箱与掉落兜底都算成功送达**，通知单主使用相同成功文本，结束订单并停止其定位粒子。

#### 9.3 动物单

成功完整扣除后，在目标位置播放**`minecraft:happy_villager`绿色成功粒子**，结束订单并停止白色定位标记。不生成箱子、掉落餐品或下单生物；物品仅被消耗。

#### 9.4 配送报酬

成功后将货币作为**掉落物实体**生成在配送员当时的XYZ，尽量合成为大面值货币。这里的生成位置是配送员位置，不是下单点；玩家单与动物单都按此发放。

货币采用Numismatics，按`sun=4096`、`crown=512`、`cog=64`、`sprocket=16`、`bevel=8`、`spur=1`大面额优先拆分；物品ID使用`numismatics:`命名空间，证据见第六节。最终收益已为非负整数且存在1单位面额，不产生面额余数。文案“已领取XXX元”由用户提供，但掉落并不等于已拾取，见文案审阅项。实现时须保证重复执行或超时竞争不会重复扣物／发奖；本轮只记录该未覆盖边界，不写代码。

### 10. 不可取消与超时失败

- 正式接单后无取消功能，只能成功完成或自然超时失败。
- 默认超时12,000秒，正式接取时开始；不是点餐时或查看预览时开始。以后可配置。
- 超时后通知配送员`【美团】当前订单已超时失败。`，结束其未完成订单状态。

### “地形查找未完成”是什么意思

这不是已经存在的功能或用户要求的额外玩法，而是此前提出的实现调度方案：动物池首次创建或过期补单时，需要为新项找地表落点。如果抽到尚未加载、尤其从未生成的区块，服务器可能需要先加载／生成地形，再执行高度与方块检查。为避免一次查看把这些工作集中到同一个tick，可以分批完成；只有采用此方案且列表尚未准备好时，才会存在“正在查找”的中间状态。已有有效缓存项不需要每次重找。

此前提示意在处理上述中间状态，不表示每次查看都要玩家反复输入命令。是否采用分批查找、就绪后自动显示列表以及是否需要聊天提示，仍待说明与确认；不能擅自通过只选已加载区块改变用户的随机落点范围，也不能直接把读取世界方块移到任意后台线程。用户尚未批准该等待提示，本轮不接入。

解释后已提出新的确认选项：分批完成查找，准备好后自动显示选单；只有列表未就绪时，在聊天栏显示`【美团】正在生成选单，请稍候。`，或采用同样的自动展示但不发送等待提示。当前等待用户回复，后续以其选择替代此前“请稍后查看”的提案。

### 配置与实现口径

统一配置：包内`pack/overrides/config/trainresync.json`及两服共享`server/shared/config/trainresync.json`的`meituan`节；共享服保留`railwayDataProtection: true`，玩家包不启用铁路保护。缺`meituan`或未启用时不开放配送命令，配置修改后重启世界／服务器生效。

- `foods`采用第5.4节结构；`animals`为中文名数组，其余范围、概率、乘数、配送半径、超时和动物有效期均可配置。火爆范围使用百分之一整数`hotMinHundredths: 150`与`hotMaxHundredths: 200`。
- 为避免异常配置造成无限掉落，数量乘数限定正整数1–64；单价及乘数须为正数，单单报酬不得超过10亿基础单位；非法配置或缺失食品／货币注册项记录服务端错误并关闭该功能。未新增玩家错误文案。
- 距离以目标方块XZ中心、目标腿部Y为基准；10格边界包含。邻格按固定dx/dz顺序选第一个空气格。自然日广播采用Asia/Shanghai，以今天及前6个自然日为近7日；已有成功配送者保留原“或”条件。
- 随机后缀为0000–9999，允许重号；订单内部使用UUID区分。世界边界附近将抽样坐标限制在世界边界内；最高方块上方越界时使用最高合法Y，整列空时用世界最低合法Y。前32次使用原版`BlockState.isSolid()`，33–64次接受无流体的非空气格，第65次放宽到任意非空气／流体。
- 地形查找只在补动物池时执行，逐任务轮转；使用原版区块Future调度，区块就绪后在服务器线程检查最高非空气格。原版`getChunkFuture`的主线程分支会阻塞，因此从它支持的非主线程入口提交调度，不在后台直接读取方块。完成后自动展示选单，**未接入仍待确认的等待提示**。
- 在线消息通过本功能的公共发送入口输出；离线结果暂只记服务端日志，等待Inbox兼容。此入口不冒充已完成的跨功能通用邮件API。
